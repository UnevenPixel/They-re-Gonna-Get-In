# AIControl

Top-level decision-maker for a computer-controlled team. One `AIBrain` per AI team, owning a `StateMachine` over three strategic postures (`build_up`, `defending`, `castle_defense`) and dispatching every order through `IssueOrderToUnits` -- the same path the player's `SelectionController` uses, so AI and player units are driven identically once an order is issued.

## AIBrain & think loop

`Step()` runs once per Step event. `thinkTimer` ticks down every frame (scaled by `global.matchSpeed`, stopping entirely when paused) and only re-evaluates the full decision cycle (`fsm.Step()`) every `AI_THINK_INTERVAL` (~0.75s) frames.

Urgency interrupt (2026-07-12, "faster reaction"): every frame, ahead of the normal timer, cheaply checks `AI_CastleUnderThreat`/`AI_DetectThreat`. If the team is under threat and not already reacting (not already `defending`/`castle_defense`), `thinkTimer` is zeroed so the full decision cycle fires that same frame instead of waiting out the rest of the interval. Only the cheap threat checks run every frame -- once already reacting, the interrupt backs off and the normal cadence resumes.

`age`/`probeCooldown` tick every frame scaled by `matchSpeed` regardless of posture -- "early game" (`AI_TryProbeAttack`'s window) is wall-clock since the brain was created, not time spent specifically in `build_up`.

`hesitancy` (2026-08-06, "delay its decisions by 75%... does not apply to reactionary actions like defending"): a per-decision-ATTEMPT countdown, not a per-frame timer -- it only moves when `AI_BuildUp_Step` actually reaches its blueprint/training block, at most once per think tick, and never while the brain is in `defending`/`castle_defense` (those states return before reaching the hesitancy check). "Delay by 75%" is read as a skip rate: skip-skip-...-act, `AI_HESITANCY_DELAY_TICKS` skips per act. Starts at 0 so the AI's very first decision after spawning isn't itself delayed; resets back to `AI_HESITANCY_DELAY_TICKS` after every act so the delay keeps recurring rather than only firing once at startup -- the request describes the skip/decrement mechanism but not this reset, so it's a judgment call. Gated at the `AI_BuildUp_Step` call site rather than inside `AI_TryTrainComposition` itself, because that function has a second call site inside `AI_TryReinforceDefense` (the "defending" emergency un-garrison-and-train reaction) which must stay un-delayed.

`AI_HESITANCY_DELAY_TICKS` bumped `3` -> `30` (2026-08-10, "update enemy hesitancy to 10 times as high") -- skip rate went from 3-of-4 (75%) to 30-of-31 (~96.8%). A straight 10x multiply on the tick count, not a re-derivation from a stated percentage this time -- flag if a specific target skip percentage was actually meant instead.

**Root cause of the opponent's opening-seconds building burst, diagnosed 2026-08-13**: `hesitancy` started at a hardcoded `0` (see the "starts at 0 so the very first decision isn't delayed" note above) -- meaning the AI's FIRST `build_up` think tick (~0.75s after spawning, `AI_THINK_INTERVAL`) ran completely un-hesitant. `AI_TryPlaceBlueprints` wasn't a one-placement-per-tick function at the time -- it looped over EVERY held blueprint stack and placed every affordable one in a single call (**2026-08-14: no longer true, see below**). Combined with the starting loadout (`oMatchControl/Create_0.gml`'s test data, one of every registered blueprint, 100 of every resource), that first un-delayed tick could place several buildings back to back almost instantly, before hesitancy's skip-cadence ever kicked in.

**Fix (2026-08-13): `hesitancy` started at `AI_HESITANCY_DELAY_TICKS * 3`** (90, at the then-current `30` reset value) instead of `0` -- "start at triple what it normally resets to," per request. This replaced the old "first decision is never delayed" behavior with "the AI's first `build_up` blueprint/training attempt is delayed at least as long as any other," closing the burst.

**2026-08-14 follow-up ("half the starting hesitancy"): the `x3` starting multiplier is now `x1.5`** -- `hesitancy = AI_HESITANCY_DELAY_TICKS * 1.5` (45 at the then-current `30` reset value, was 90). This halved the earlier fix's own multiplier, not `AI_HESITANCY_DELAY_TICKS` itself (the recurring per-act reset value, `30` at the time, was untouched -- "starting hesitancy" was read as the one-time initial value set in `AIBrain()`'s constructor, not the ongoing skip-cadence). The tutorial-completion reset (`TutorialGuideScripts.gml`, "Guided tutorial gate" below) used this exact same formula and was updated to match at the time, so the AI resumed post-tutorial at the same (then-halved) starting hesitancy it would have had fresh out of the constructor -- **2026-08-16 follow-up: that tutorial-completion reset has since been REMOVED entirely, see below.**

**2026-08-16 follow-up ("half all AI Hesitancy"): `AI_HESITANCY_DELAY_TICKS` itself halved `30` -> `15`.** Unlike the 2026-08-14 follow-up above (which only touched the one-time starting multiplier), this changes the RECURRING reset value every `build_up` decision uses -- skip rate drops from ~96.8% (30-of-31) to ~93.3% (15-of-16). Every derived value follows automatically without its own edit: the constructor's `hesitancy = AI_HESITANCY_DELAY_TICKS * 1.5` now starts at 22.5 (was 45); at `AI_THINK_INTERVAL` (~0.75s/tick) and `matchSpeed = 1`, that's roughly **~17 seconds** before the AI's first `build_up` blueprint/training attempt (down from ~34s). Same caveat as every prior pass on this value: worth an in-engine feel check, since this remains a literal halving of an already-untuned placeholder, not a re-derivation from any stated target.

**`AI_TryPlaceBlueprints` capped to one placement per call (2026-08-14, "only place one building at a time")**: previously looped over every held blueprint stack across both passes and placed every affordable one in a single call (see the burst root-cause above). Now returns immediately on the first successful `TryPlaceBlueprint()` call, in either pass -- pass 1 (missing-resource-producer priority) is checked first; pass 2 (greedy "spend whatever's affordable") only runs at all if pass 1 placed nothing. Combined with hesitancy, the AI now places at most one building per un-hesitant think tick, rather than potentially several. `AI_NextAffordableBlueprint` (a query-only helper elsewhere in this file, mirrors pass 2's search logic to answer "what would the AI build next" without placing anything) was NOT touched -- it doesn't place buildings, so the one-at-a-time change doesn't apply to it.

## Guided tutorial gate (2026-08-13, scaffolding for the upcoming guided-tutorial gameplay pass)

`AIBrain.Step()` now early-returns, before anything else, while `global.tutorialActive` is true -- "pause enemy actions" during the guided tutorial. This is a hard freeze, not a no-decisions-but-still-ticking pause: `age`/`probeCooldown`/`thinkTimer` also stop advancing (the return happens before any of them are touched), so once `tutorialActive` clears the brain resumes exactly where its internal clocks left off rather than getting a free "skipped time" head start or falling behind.

`global.tutorialActive` isn't new -- it's the same flag `HubControlScripts.gml` declares and `WarRoomMenuScripts.gml`'s tutorial-completion work (see that file's .md) already made span the whole first run, only clearing via `CompleteTutorial()` (`PlayerSaveDataScripts.gml`) at that run's end. This gate is the first GAMEPLAY consumer of it -- previously it only affected hub-town/war-room UI gating, never anything inside a match.

**"Limit player actions" (the other half of the request) is explicitly DEFERRED, not built this pass.** Confirmed with the user: wire the flag and pause the enemy now; player-side restrictions wait for a later pass once actual guided-tutorial steps/content exist to define what should be limited. No player-facing gate exists anywhere yet -- `SelectionController`/`IssueOrderToUnits`/`BlueprintController` are all untouched by `tutorialActive` as of this writing.

## AI defensive posture

2026-07-12 follow-up ("don't steamroll me"): plot-tier classification, a fraction-of-total-army reserve floor that siege/probe commitments must respect, and proactive coverage spread across owned buildings. Replaces an old flat guard-only, headcount-of-2 reserve.

`AI_PLOT_TIER_REAR/MID/FRONT` mirror the existing `oBuildingPlot.inside`/`far` grouping `SpawnBuildingPlot` (`PlotScripts.gml`) already tags every plot with (`oPlotSpawner`'s castle grid = REAR, `oOuterPlotSpawner`'s near/far bands = MID/FRONT) -- not a new geometry system. `AI_BuildingPlotTier` looks up a building's plot by position (`instance_position`, the same technique `BuildingFreePlot` uses) since no plot reference is stored on building instances anywhere in this codebase.

`AI_PartitionByPosture` splits a unit array into guard/defend buckets, shared by `AI_ReserveDefensiveUnits` and `AI_TryProbeAttack`.

`AI_MinDefensiveReserve`: `ceil(totalArmy * AI_MIN_DEFENSIVE_ARMY_FRACTION)`, where `totalArmy` = live units + stationed units ("leave at least 1/4 of its army to defend/guard/station at any given time"). Stationed units count toward this automatically since they can never be sent to siege/probe/attack at all (a different object, `oUnitStationed`).

`AI_ReserveDefensiveUnits` reserves "defend" units FIRST, up to the requested count -- they're already actively posted at a specific building, so pulling an idle "guard" unit instead "costs" less. "Guard" only fills whatever gap remains after "defend" is exhausted. If there aren't enough units to meet the reserve, ALL of them are reserved (surplus may be empty) -- an empty/under-strength offensive commitment is preferable to breaking the defensive floor.

`AI_UncoveredBuildingsByTier`: every owned, placed building with zero live "defend" units currently posted to it, bucketed REAR-first then MID then FRONT ("spreads its defensive force around its buildings... prioritizing its rear plots"). Recomputed fresh every call (cheap at this game's scale). 2026-07-13 (playtesting checklist item 2, "during the first age, only prioritize protecting production buildings"): while `global.age[_team] == 1`, training buildings are excluded from this list entirely -- PROACTIVE coverage only; a training building actually under attack still triggers "defending" and pulls responders exactly as before.

`AI_TryMaintainDefensiveSpread`: posts idle "guard" units to "defend" the first uncovered building (REAR-first), at most `AI_SPREAD_ATTEMPTS_PER_TICK` per think tick -- gradual, not a lump reassignment. Only ever pulls from "guard", never reassigns an already-"defend" unit. Called before `AI_TryStationUnits` in `AI_BuildUp_Step`: physical coverage at every building takes priority over the passive stationed-bonus optimization, since an undefended building can be lost outright while delayed stationing only costs an economic edge. Scope: guarantees at least one defender per building, not any particular garrison size.

## Posture state handlers

### build_up (`AI_BuildUp_Step`)

The AI's default economic/training/massing posture. Each think tick, in order:

1. Castle threat check (`AI_CastleUnderThreat`) -> hands off to `castle_defense`. Outranks everything else.
2. Ordinary building threat check (`AI_DetectThreat`) -> hands off to `defending`, but ONLY if `AI_TeamHasTrainingStructures` OR `AI_TeamHasUnitsInHand` is also true (2026-08-16 follow-up, "do not switch AI state to defending buildings if there is no unit training structures... cannot defend itself if it has no buildings"; **round 2 follow-up, "allow for defending with units in hand without training buildings"**). A team with zero live `oTrainingBuildingParent` instances has no way to ever train a replacement unit -- entering `defending` over a threatened building with NEITHER a training structure NOR any units on hand would eventually just fall into `AI_TryReinforceDefense` (once it runs out of live units) trying to queue training that can never succeed, so that specific case is skipped, staying in `build_up` to keep trying to rebuild the economy instead. But a team with units already deployed or stationed clearly CAN defend itself even with zero training buildings (`AI_TeamHasUnitsInHand` checks both `GatherTeamUnits` and `AI_CurrentStationedCount` -- stationed units in particular don't need a training building to be un-garrisoned, see `AI_TryReinforceDefense`), so that case is explicitly allowed through. Only truly "nothing to defend with and no way to ever get anything" skips the transition.
3. Hesitancy-gated blueprint placement (`AI_TryPlaceBlueprints`) + training (`AI_TryTrainComposition`), wrapped in `AI_HideGoldReserve`/`AI_RestoreGoldReserve` so this spending can never eat into the emergency gold reserve.
4. Defensive spread (`AI_TryMaintainDefensiveSpread`).
5. Stationing (`AI_TryStationUnits`).
6. Gathers every available unit and carves out `AI_MinDefensiveReserve`'s floor (`AI_ReserveDefensiveUnits`) -- whatever's left is `_surplus`.
7. Offers `_surplus` to `AI_TryProbeAttack` (early-game harassment, separate budget from siege).
8. Offers what's left to `AI_TryAttackSurplusAtCap` (2026-07-13, "use deployed units when at unit cap").
9. Whatever's left after that, once its `AI_ArmyPower` reaches `AI_SiegePowerThreshold`, commits to `siege` against the enemy castle.

Step 7/8 are new outlets layered AHEAD of the siege check in step 9 -- per explicit clarification they don't change when siege itself fires, only give surplus something to do before it's evaluated for siege.

### defending (`AI_Defending_Step`)

Entered from `build_up` the instant `AI_DetectThreat` finds a threatened owned building. Escalates to `castle_defense` if the castle also comes under threat (same priority as `build_up`); reverts to `build_up` once nothing's threatened.

2026-07-12 ("moving units to defend different buildings"): uses `AI_DetectThreats` (plural) and distributes every available unit across ALL threatened buildings by nearest-with-tier-penalty score (`distance + AI_BuildingPlotTier(building) * AI_DEFEND_TIER_WEIGHT`) rather than dumping everyone on the first building found -- REAR buildings get no penalty, MID/FRONT get progressively larger ones, biasing responders toward rear without overriding a unit overwhelmingly closer to a FRONT building. Orders are grouped into one `IssueOrderToUnits` call PER building (not per unit) so `DefendBuildingWaypoints` only re-evaluates once per building per tick.

Economy/training pauses while defending -- a deliberate scope choice. 2026-07-13 EXCEPTION: if the team has literally ZERO live units, `AI_TryReinforceDefense` runs first ("check if it has any deployed units; if not, train more or un-garrison from the castle").

`AI_TryReinforceDefense`: un-garrisons every affordable stationed unit (any type, via `AI_FirstStationedType`) up to `AI_REINFORCE_MAX_DEPLOYS` (a runaway-loop safety net, not a real gameplay limit -- `DeployStationedUnit`'s own affordability check is what actually stops it), and queues training via `AI_TryTrainComposition` in the same tick. Neither step is gold-reserve-gated -- the reserve exists specifically so this "zero army, under attack" emergency has real gold to spend.

### castle_defense (`AI_CastleDefense_Step`)

The AI's HIGHEST priority posture (2026-07-06: "if under siege, top priority is defeating enemies attacking the castle"). Entered from either `build_up` or `defending` the instant `AI_CastleUnderThreat` is true. Losing the castle loses the match outright, so this recalls units the other two postures deliberately leave alone: every unit in "guard", "defend", OR "siege" -- including a siege already committed against the ENEMY castle -- is redirected to defend the home castle via `CastleDefendWaypoints` (not `DefendBuildingWaypoints` -- see `Defend_Enter`'s castle-vs-building branch). Recalling an in-progress siege is an intentional behavior change from an earlier, more conservative version that left mid-siege units alone. Units already actively fighting (combat/combatRanged/attack/attackRanged) are left alone -- pulling a unit out of a live engagement tends to just get it killed mid-retreat. Reverts to `build_up` once the castle is clear.

## AI perception

Threat detection and rough combat-power estimation, added 2026-07-06 alongside `defending` and the strength-based siege trigger.

`AI_DetectThreat`/`AI_DetectThreats` are deliberately BUILDING-scoped, never castle-scoped: redirecting responders through the existing "defend" order only works cleanly against a real ~48x48 `oBuildingParent` -- `DefendBuildingWaypoints` hardcodes that box size (`DEFEND_BUILDING_HALF`). The castle is a completely different size, which is why `AI_CastleUnderThreat`/`AI_CastleDefense_Step` are a separate castle-scoped path (via `CastleDefendWaypoints`) instead of being folded into these functions. `AI_DetectThreat` stops at the first threatened building (a cheap early-exit used by `AI_BuildUp_Step`'s posture-transition guard and `AIBrain.Step`'s urgency interrupt, neither of which needs the full list); `AI_DetectThreats` (2026-07-12, plural) returns every threatened building for `AI_Defending_Step`'s per-building distribution.

`AI_CastleUnderThreat`: true if any enemy unit is within `AI_CASTLE_THREAT_RADIUS` of the team's own castle. Checked FIRST, ahead of `AI_DetectThreat`, in both `build_up` and `defending`.

`AI_UnitPowerScore`/`AI_ArmyPower`: rough single-unit/summed combat-power estimate (current HP + attackDamage, weighted by `AI_POWER_HEALTH_WEIGHT`/`AI_POWER_DAMAGE_WEIGHT`) -- just enough to stop the AI treating a fresh Peasant and a fresh Mud Golem as equally "one unit" toward a siege decision. Doesn't account for range, cooldown, melee vs ranged, or tags.

`AI_TeamAtArmyLimit`: true once live + stationed + queued reaches `global.armyLimit[_team]` -- the SAME saturation check `TrainingTryQueueUnit` uses to reject a new queue attempt, factored out so `AI_SiegePowerThreshold`/`AI_TryStationUnits` can react to it too (2026-07-13, "if the AI has reached army limit, it should utilize those units in one way or another"). Correctly counts stationed units -- they still count against `global.armyLimit`, they don't shrink the army for cap purposes.

`AI_SiegePowerThreshold`: `AI_SIEGE_POWER_FRACTION` of `CASTLE_MAX_HEALTH` -- both flagged placeholders, not a balanced formula, just giving the AI some sense of scale instead of a flat headcount. 2026-07-13 follow-up: drops to the much smaller `AI_SIEGE_POWER_FRACTION_AT_CAP` once `AI_TeamAtArmyLimit` is true. Diagnosed 2026-07-13: at the flat 0.6 fraction, a 6-unit (`global.armyLimit`) Peasant/Archer army tops out around 114 power against a ~300 bar -- mathematically unreachable, so the AI would sit at the cap forever, never sieging. Only kicks in once the team is actually capped; a team still building up normally is still gated by the full fraction.

## AI economy

Reuses the exact same functions the player's UI calls (`TryPlaceBlueprint`, `TrainingTryQueueUnit`), so AI-built structures and AI-trained units go through identical cost/limit/analytics handling. Both were originally "deliberately greedy/simple" (spend whatever's affordable, train at every building, no priority) -- reworked 2026-07-06 to prioritize replacing a missing/depleted resource producer and to weight training toward under-represented tags, both still falling back to the old greedy behavior once their priority is satisfied.

`AI_CheapestStationCost`: lowest `stationCost` across every registered unit type (team-independent). Sizes the gold reserve against whatever the CHEAPEST redeployable unit would cost, since the AI can't know in advance which type(s) it'll need to un-garrison during a future emergency.

`AI_GoldReserveAmount`/`AI_HideGoldReserve`/`AI_RestoreGoldReserve` (2026-07-13, "make sure the AI is keeping a reserve of gold"): sized to cover redeploying `AI_GOLD_RESERVE_UNIT_COUNT` stationed units at the cheapest registered cost. Hide/restore is a bracket pattern -- hide before ordinary economy spending (`AI_TryPlaceBlueprints`/`AI_TryTrainComposition` in `AI_BuildUp_Step`), restore immediately after, nothing else touches the team's gold in between. Deliberately NOT used around `AI_TryReinforceDefense`'s own spending -- the whole point of the reserve is to have real gold available for exactly that emergency, so that path spends freely, reserve included.

`AI_FindEmptyOwnedPlot`: first unblocked, unoccupied owned plot. Still has no general inside/outside cost preference as of this writing (the AI will place a resource building on a full-price Exterior plot when a discounted Castle plot sits empty, and never seeks Distant plots for their stat bonus) -- flagged as a real but minor AI inefficiency, not fixed here, out of scope for this pass. Optional `_preferInside` (2026-07-13, "build the Peasant Ward inside the castle to begin with"): does a first pass over inside-only plots before falling back to any plot -- used by `AI_TryPlaceBlueprints` for training buildings whose trained unit favors stationing (`AI_UnitFavorsStationing`), since a training building on an inside plot spawns every unit directly as stationed (`TrainingSpawnUnit`'s `_building.inside` branch), skipping the "train live, then separately order it to station" step. This does NOT bypass `global.armyLimit` -- stationed units still count against it; the benefit is purely the discounted placement cost plus skipping the manual station step.

`AI_MissingResourceProducers`: which of the 5 producible tier-1 resources (wheat/water/wood/gold/iron) have zero live producing buildings. Resource buildings self-destroy on hitting their lifetime `resourceLimit` and nothing replaces them automatically -- this is what lets placement notice and prioritize a replacement.

`AI_TryPlaceBlueprints`: two passes over `global.blueprints[_team]`, both iterated BACKWARDS deliberately -- a successful placement calls `RemoveBlueprintOne`, which can `array_delete` the stack it just consumed, and backwards iteration means that shift never affects indices still to be visited. Pass 1: if some resource has zero producers, any held blueprint producing one gets first claim on this tick's affordability. Pass 2 (only reached if pass 1 placed nothing): every remaining affordable blueprint, same greedy "spend whatever's affordable" priority as before. A training building whose trained unit favors stationing seeks an inside plot first in pass 2 (see `AI_FindEmptyOwnedPlot` above); every other blueprint keeps the old no-preference behavior. **2026-08-14 ("only place one building at a time"): the function now returns on the FIRST successful placement in either pass**, rather than continuing to place every remaining affordable stack -- was the root cause of the opening-seconds building burst (see "Root cause..." above), so this closes that same class of issue from a different angle (the earlier `hesitancy`-starting-value fix only delayed WHEN the first tick could act, this caps HOW MUCH it can do once it does).

`AI_ArmyTagFraction`: fraction of the team's CURRENT LIVE army carrying a given tag -- deliberately doesn't count what's still queued/training (unlike the hard caps in `TrainingScripts.gml`, which must count queued units to avoid overshooting a limit). Composition targeting is a soft preference, so a big finished wave relaxes it immediately instead of waiting on an already-committed queue.

`AI_TryTrainComposition`: checks "tank" then "ranged" fraction against `AI_TANK_TARGET_RATIO`/`AI_RANGED_TARGET_RATIO`; whichever is furthest under target (tank checked first) becomes the wanted tag, and every owned building training a matching-tagged unit is attempted first. Every OTHER owned training building (not already attempted) is then attempted too, so affordable training never sits idle once composition goals are met, or for buildings training an untagged unit entirely.

## AI stationing

2026-07-12 "use stationed units" request: the AI converts some of its own idle "guard" units into stationed units for their passive bonuses, the same mechanism a player uses via the castle garrison dropdown -- automated, gradual, and reserve-aware so it doesn't hollow out its own standing defense.

`AI_CurrentStationedCount`: thin wrapper around the shared `CountTeamStationedUnits` (`StationScripts.gml`) -- kept as its own AI-prefixed name since every call site in this file already uses it, but the counting logic itself lives in one place.

`AI_UnitStationedBonusValue`: sum of a unit type's `stationedBonuses[].amount` -- a rough "how much value does this type gain from being stationed" score. 0 for a unit with no `stationedBonuses` at all (Archer, per its own scope note in `UnitDefinitions.gml`) -- such units are never worth auto-stationing.

`AI_UnitDefPowerScore`: definition-level counterpart to `AI_UnitPowerScore` (same formula, off `maxHealth`/`attackDamage` instead of a live instance's current HP) -- needed because `AI_UnitFavorsStationing` compares unit TYPES before any instance of one necessarily exists (e.g. deciding where to place a not-yet-built training building).

`AI_UnitFavorsStationing`: true only when BOTH (1) the unit actually gains something from stationing (`AI_UnitStationedBonusValue > 0`) AND (2) its definition-level power sits below the flat `AI_STATION_FAVOR_POWER_CEILING` cutoff. A flat cutoff was chosen over a registry-wide relative comparison for simplicity -- doesn't need to iterate the whole unit registry, and is just as valid a placeholder as everything else in this file. Only Peasant (14) clears it as of this writing; Soldier (33)/Knight (40)/Mud Golem (65)/Bomb Goblin (102, skewed high by its one-shot attack) all sit above it.

`AI_TryStationUnits`: called once per think tick from `build_up` only (never while defending/castle_defense). No-ops at `AI_STATION_MAX_STATIONED`. Reserve floor is `AI_STATION_MIN_GUARD_RESERVE`, dropping to the smaller `AI_STATION_MIN_GUARD_RESERVE_AT_CAP` once `AI_TeamAtArmyLimit` (2026-07-13: holding back guards protects a future training pipeline, but once the team is AT its cap there's no pipeline left to protect either way -- converting more guards to stationed at that point is purely for their own passive value, NOT an army-cap workaround, since stationed units still count against `global.armyLimit`). Only guards with a nonzero `AI_UnitStationedBonusValue` are eligible; among those, WEAKEST-power-first goes first (a unit that contributes little in a fight loses little sitting in the garrison -- the same logic that makes a weak-melee-but-strong-stationed-bonus Peasant worth stationing), `stationCost` only as a final tiebreaker (preserving some of the old greedy-affordability behavior when power scores tie). The reserve floor is checked against the TOTAL guard count, not just eligible ones -- ineligible guards still count as "kept back" even though they'd never be picked anyway. Posts at most `AI_STATION_ATTEMPTS_PER_TICK` per tick, gradual rather than a lump conversion.

## AI probe attacks & cap-surplus attack

2026-07-12 "add an early game probe attack" request: small, cheap harassment against an ordinary enemy building via the same "attack" order/state a player uses, deliberately separate from siege (which targets the enemy CASTLE specifically and needs the much higher `AI_SiegePowerThreshold` bar).

`AI_TryProbeAttack`: called once per tick from `build_up`, AFTER the defensive-floor reserve has already been carved out of the surplus -- probes draw from the SAME uncommitted pool siege does, so they respect `AI_MIN_DEFENSIVE_ARMY_FRACTION` too. No-ops (returns surplus unchanged) past `AI_PROBE_WINDOW_FRAMES` (early game only), during cooldown, with too little surplus, or if the enemy owns no building at all. On a successful probe: picks ONE random standing enemy building (never the castle -- "attack" is building-only, matching its player-facing scope), sends up to `AI_PROBE_ATTACK_SIZE` units at it (preferring GUARD units over DEFEND units within the surplus, same priority `AI_ReserveDefensiveUnits` uses), then resets the cooldown. Does NOT check the target's own defenses -- a probe that gets its raiders killed against a defended building is expected behavior (that IS the information it's gathering), not a bug.

`AI_CanReplaceDeployedUnits` (2026-07-13, "use the AI's deployed units when unit cap is reached... after it determines it can replace those units"): true if EITHER (a) at least one owned training building can currently afford its OWN `trainCost` right now (deliberately does NOT check `TrainingTypeLimit`/`global.armyLimit` here -- those caps are exactly what sending surplus off to attack is about to relieve, so gating on them being already-clear would be circular), OR (b) the team's owned training buildings collectively train 2+ DISTINCT unit types ("train other units in their place").

`AI_TryAttackSurplusAtCap` (2026-07-13): once the team is at its army cap AND `AI_CanReplaceDeployedUnits` says it's ready to lose some units, redirects the ENTIRE remaining surplus to attack one random ordinary enemy building (never the castle, same scope as the probe) -- a NEW, additional outlet layered AHEAD of the existing siege check, which it does NOT change. If the enemy has no ordinary buildings left (only their castle remains), returns surplus completely untouched so the unchanged at-cap siege logic below handles that case. Committing the ENTIRE surplus (not a token slice, no cooldown the way the probe has) is a judgment call, not an explicit spec answer -- flag if a partial commitment or its own cooldown reads better once playtested.

## AI debug introspection

2026-07-13 request ("add AI debug data to the list on the right of the UI stating its quotas, and what it is intending to do next"), rendered from `oAIControl/Draw_64.gml`. Everything in this section is READ-ONLY: it inspects current state and re-checks the same conditions the real decision functions already gate on, but never issues an order, spends anything, or mutates a queue. Some duplication of that gating logic is deliberate -- a dry-run preview needs to answer "would this succeed" without the real side effects, and there's no non-mutating variant of `TrainingTryQueueUnit` to call instead. Flagging the duplication risk: if `TrainingTryQueueUnit`'s own gates change, `AI_WouldTrainSucceed` needs a matching update, or this readout will quietly drift out of sync with real behavior (display-only drift, not a functional bug either way, but worth knowing about).

`AI_WouldTrainSucceed`: dry-run mirror of `TrainingTryQueueUnit`'s three gates (type limit, army-wide limit, affordability) for one additional unit. 2026-07-13 corrections keep both gates in sync with `TrainingTryQueueUnit`'s own corrected stationed-unit counting.

`AI_NextAffordableBlueprintName`: first held blueprint that's affordable AND has a free plot -- mirrors `AI_TryPlaceBlueprints`' second (greedy) pass only, not its resource-priority first pass. Good enough for a debug readout, not a full re-derivation.

`AI_NextTrainableUnitName`/`AI_TeamHasSpareGuard`/`AI_NextStationCandidateName`: dry-run mirrors of the corresponding real training/spread/stationing selection logic.

`AI_DebugIntent`: previews what the brain's NEXT think tick would do, mirroring `build_up`/`defending`/`castle_defense`'s own priority order (castle defense > building defense > blueprints > training > defensive spread > stationing > siege > probe > idle), stopping at the first applicable action instead of doing it. Not guaranteed to exactly match the real next tick -- state can shift between frames (e.g. a threat appearing) -- good enough for a debug readout, not a substitute for reading the real functions.

`AI_DebugQuotasText`: one newline-joined block of the raw quota numbers driving this tick's decisions, recomputed fresh every call. 2026-07-13 correction: the Army line shows live + stationed + queued, all three, against `global.armyLimit` -- a live+queued-only line could misleadingly suggest room existed that stationed units had already used up.

## 2026-10-15: defending targets the building actually under attack

Symptom: with an enemy at the top front building, AI defenders hung around lower buildings. Cause: `AI_THREAT_RADIUS` (250) is wide enough that neighboring buildings in the same column are flagged threatened too, and `AI_Defending_Step`'s score (`distance + tier * AI_DEFEND_TIER_WEIGHT`) penalizes FRONT plots by 400, so units were assigned to the REAR/MID neighbors, where they patrol their perimeter and only aggro within `attackAggroRadius` (~96-140) -- never reaching the intruder. Fix: new `AI_BuildingsEngagedByEnemy(_team, _buildings)` narrows the candidate list to buildings with an enemy within `AI_DEFEND_ENGAGE_RADIUS` (120); if any exist, only those receive defenders (tier bias still applies among them). If none are that close, the old wide list is used unchanged. The unit-level `defend` state was NOT touched. Untuned: the 120 radius. The tier bias still applies when several buildings are genuinely engaged, so a lone front attack can still pull some units to a rear building under attack at the same time.
