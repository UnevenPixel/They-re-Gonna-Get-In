## Booger's HUD presence

Drawn from THREE separate call sites in `oUnitControl/Draw_64.gml` (2026-08-14, was two -- see Speech bubble below):

- `Draw_Front()` -- called right after the persistent bar sprites + `rulerPortraitController.Draw(...)`, before `DrawTrainingQueueBars()`. Draws `sBoogerHands`, always above the bar (2026-08-14, see Hands below). No longer draws the speech bubble -- see `Draw_Bubble()` next.
- `Draw_Bubble()` (2026-08-14, new) -- called AFTER `DrawTrainingQueueBars()`, so the speech bubble renders ON TOP of the training-queue progress bars instead of underneath them (per request: "draw Booger's speech bubble over top the unit building production bar"). **Horizontal position -- `TUTORIAL_GUIDE_SCREEN_FRACTION_X = 4/5` (2026-08-13, second follow-up -- supersedes the 2/3 value from the first follow-up).** `TUTORIAL_GUIDE_X` is a derived macro, not a literal: `display_get_gui_width() * TUTORIAL_GUIDE_SCREEN_FRACTION_X + spriteWidth*scale/2` -- solved so `_VisualCenterX()` (her drawn sprite's true horizontal center, accounting for the flip) lands EXACTLY on the fraction's mark (1536 at the nominal 1920 GUI width), rather than hardcoding the resulting pixel value. Same "#macro embeds a function call, evaluated live at each use site" pattern `DIALOGUE_SPEAKER_TEXT_COLOR` already established (`DialogueOverlayScripts.gml`) -- stays correct if `display_get_gui_width()` or `sBoogerPortrait`'s dimensions ever change, rather than silently drifting out of sync like a hardcoded literal would. At 4/5 her drawn sprite spans roughly x=1295-1777, comfortably inside the 1920-wide GUI (computed directly, not assumed).

**Scale -- `TUTORIAL_GUIDE_SCALE = 2`, matching the UI bar/ruler-portrait's own established 2x convention.** Not specified in the request; every other element on this bar uses this same scale, so it was the obvious default rather than inventing a new one.

## Animation -- shared arch curve, played forward or backward

**`_AnimCurveY(_t)`, `_t` 0..1, is the ENTIRE appear transition as one curve**: `_t=0` -> `_StartY()` (fully off-screen), `_t=_RiseFraction()` -> `_OvershootY()` (the arch's peak, `TUTORIAL_GUIDE_OVERSHOOT` = 48px past rest), `_t=1` -> `_RestY()` (settled). Two legs:

- **Start -> overshoot** (`_t` 0..`_RiseFraction()`): ease-OUT cubic (`1 - (1-t)^3`) -- fast start, decelerating INTO the overshoot peak. Duration `TUTORIAL_GUIDE_RISE_SECONDS` (0.45s, judgment call).
- **Overshoot -> rest** (`_t` `_RiseFraction()`..1): smoothstep (`t^2*(3-2t)`) -- a gentle, symmetric ease-in-out for the short "settle back down" correction. Duration `TUTORIAL_GUIDE_SETTLE_SECONDS` (0.22s, judgment call).

Two explicit legs with an exact 48px overshoot waypoint were chosen over a single parametric "back-ease" formula (the standard `1 + c3*(t-1)^3 + c1*(t-1)^2` overshoot tween, which most tweening libraries use for this exact "rise and settle" feel) specifically because a back-ease's overshoot amount is a PERCENTAGE of total travel distance (via its `c1` constant), not a literal pixel value -- the request asks for an exact "overshoots by 48px", which a two-waypoint curve guarantees regardless of how far she's travelling, where a single back-ease formula would need extra calibration to hit an exact px target. The two eases chosen (cubic ease-out into the peak, smoothstep for the settle) are what produce the "arch" FEEL the request describes (a curved deceleration into the peak, not a linear rise-then-instant-drop) without literally being a back-ease formula.

**Appearing samples `_t` = `animTimer / totalDuration` (0->1, forward). Disappearing samples `_t` = `1 - (animTimer / totalDuration)`** -- i.e., disappearing is the LITERAL same curve, played backward in time, per request ("reverse this animation... with the same smoothing"). This single mechanism is what naturally produces "raise up 48px, then drop below the screen" for disappearing: at disappear-start, effective `_t` starts at 1 (rest) and DECREASES, first crossing the overshoot->rest leg backward (rest -> overshoot, a rise of exactly 48px) before crossing the start->overshoot leg backward (overshoot -> fully hidden, the long drop). No separate disappear-specific keyframes or easing were written -- same function, same constants, just time-reversed.

`TUTORIAL_GUIDE_OFFSCREEN_MARGIN` (40px, judgment call) pads `_StartY()` past the point where her sprite's top edge would just barely touch the visible GUI height, so there's no risk of a stray 1px sliver showing before she starts rising.

## Speech bubble (`sSpeechBubbleInGame`)

**Sizing mirrors `HoverCardScripts.gml`'s established "smallest sprite/frame that fits, capped at the largest" pattern** (`ChooseHoverCardSprite`/`HoverCardRequiredHeight`) -- `ChooseTutorialBubbleFrame(_requiredHeight)` is the direct analog, just picking a FRAME index (0/1/2) of one sprite asset instead of three separate sprite assets, since that's how `sSpeechBubbleInGame` was built (3 frames, all sharing one 348x230 canvas and one bottom-right origin point `(348, 230)` -- confirmed via its `.yy`). Frames 0/1 are shorter than the full 230px canvas (169/200px of actual visible bubble art respectively) with transparent padding baked in at the TOP of the frame, so all three frames still bottom-align correctly from the same single origin/draw call with no extra positioning logic needed -- this is what "all are aligned to the bottom of the sprite" describes, and it falls out automatically from how the art was authored, not from anything in this code.

**`Say()` now takes an optional `_forceFrame` argument that skips `ChooseTutorialBubbleFrame`'s auto-fit entirely** (2026-08-13: "use the smallest speech bubble for these, as the largest one is too big for how much text is here" -- the auto-fit's `get_height()`-based measurement was landing on frame 1 or 2 for some of the intro script's lines even though the text reads fine smaller). `StartIntroScript()`'s 4 step entries all carry `frame: 0`, and `_AdvanceScript()` threads it through to `Say()`. The auto-fit function itself (`ChooseTutorialBubbleFrame`) is left intact and still the DEFAULT when `_forceFrame` is omitted, so a future, longer tutorial script can go back to auto-sizing just by not setting `frame` on its step data. **Flag: forcing frame 0 for all 4 lines means longer lines may visually overflow the 169px-tall frame's art if the wrapped text ends up taller than that** -- this is what was explicitly asked for, not a defensive fallback, so no clamp/truncation was added; worth an in-engine look at the actual wrapped line counts if any line reads as cramped.

**Origin is bottom-RIGHT, not bottom-left** (`xorigin=348=width`) -- the bubble is anchored by its bottom-right corner and extends up-and-left from the draw point. **The bubble sits to Booger's LEFT, not her right** (flipped from the original design during the first "move her right" pass, since a right-side bubble would have run off the 1920-wide GUI). `_DrawBubble()`/`_BubbleRect()` position that bottom-right anchor `TUTORIAL_BUBBLE_GAP_X` (24px, judgment call) to the LEFT of Booger's visual center (`_bx = _VisualCenterX() - TUTORIAL_BUBBLE_GAP_X`), and the bubble extends further left from there (its own width, up to 696px at scale 2). At the current 4/5 position the bubble spans roughly x=816-1512, still fully on screen.

**Flag: the bubble visually overlaps Booger's own visible sliver by roughly 217px, at ANY horizontal position.** Computed directly: her visible sliver is `spriteWidth*scale` (482px) wide centered on `_VisualCenterX()`, so it extends `241px` to either side; the bubble's near edge sits only `TUTORIAL_BUBBLE_GAP_X` (24px) to the left of that same center, so the bubble's right ~217px (`241 - 24`) fall inside Booger's own sliver's horizontal span. Since `_DrawBubble()` draws AFTER Booger (Draw_Front() runs after Draw_Behind()), that means the bubble can render on top of the right portion of her visible face/body. This is independent of `TUTORIAL_GUIDE_SCREEN_FRACTION_X` (2/3, then 4/5 -- both had it) since `GAP_X` and both sprites' widths never changed. Not something either repositioning request asked to fix, and not fixed here -- flagging because it's directly adjacent to the geometry this pass touched twice. Worth an in-engine look; if it reads as a real problem, increasing `TUTORIAL_BUBBLE_GAP_X` past 241px would clear it entirely (at a cost of a bigger horizontal gap between her and the bubble).

**Text**: top-left of the CHOSEN FRAME's visible region (not the full 230px canvas -- see above), `TUTORIAL_BUBBLE_BUFFER` (8px) buffer both axes, per request. **Wrap width is a fixed `TUTORIAL_BUBBLE_TEXT_MAX_WIDTH` (312 native px, 2026-08-13 request) -- NOT derived from `sprite_get_width(sSpeechBubbleInGame)` anymore.** The original formula (sprite width minus buffer) assumed the full 348px canvas was safe text space; per this request the sprite actually has a tail with a horizontal gap baked into its right side, so the previous wrap (664 screen px at scale 2) let text run into/past that gap. 312 is the caller-specified safe figure, used directly (`TUTORIAL_BUBBLE_TEXT_MAX_WIDTH * TUTORIAL_GUIDE_SCALE` = 624 screen px) rather than re-derived from the sprite or further reduced by `TUTORIAL_BUBBLE_BUFFER` -- the 312 figure is treated as already being the max TEXT width, with `BUFFER` remaining purely a text-origin offset from the frame's top-left corner, not a second width deduction. Font is `HOVER_CARD_BODY_FONT` (unchanged); default color is `DIALOGUE_SPEAKER_TEXT_COLOR` (`DialogueOverlayScripts.gml`) per request ("use the speaker font color we came up with earlier"); `Say()`'s optional `_color` argument overrides it per line (used once per phase, for the highlighted instruction line -- see Script below).

**Typewriter + voice blip** mirror `DialogueOverlayScripts.gml`'s own approach (same `.reveal()` mechanism, same `TUTORIAL_BUBBLE_TYPEWRITER_CHARS_PER_SECOND = 40` rate, same per-character throttled blip formula reusing `DialogueOverlayScripts.gml`'s `DIALOGUE_TEXT_BLIP_PITCH_MIN/MAX`/`DIALOGUE_TEXT_BLIP_OVERLAP_MS` macros and the same SFX-volume/pitch-variation treatment) -- **duplicated into this file rather than factored into a shared function.** `DialogueOverlay` and `TutorialGuide` are separate structs with no common base, and extracting the pattern would mean touching `DialogueOverlayScripts.gml`'s already-working code in an already-large pass; flagged as a known, small duplication worth a future de-dup pass rather than done here. `aBoogerSpeak` is hardcoded as the blip sound (Booger is the only voice this system uses today).

**Advancing/dismissing on click, not a timer (2026-08-13, replaced the original fixed-wait design).** Once `typewriterDone`, `_UpdateBubble` checks `mouse_check_button_pressed(mb_left)` each Step and, on a press, hit-tests the GUI-space mouse point against `_BubbleRect()` and `_BoogerRect()` -- a hit on EITHER (per request: "the player clicks on the speech bubble or Booger") either calls `_AdvanceScript()` (if there's a next line in the current phase) or `Hide()` (if this is the phase's LAST line -- 2026-08-13 follow-up, see Script content below for why the dismiss doesn't itself start the next phase). `_BubbleRect()`/`_BoogerRect()` return the exact same `{x1,y1,x2,y2}` geometry their respective draw calls use (`_DrawBubble()` reads its draw position/text placement FROM `_BubbleRect()` rather than recomputing it separately), so the clickable area can't silently drift out of sync with what's actually on screen. `_BoogerRect()` is clipped to just the sliver of her currently visible above the bar (`y1` = her sprite's top edge, `y2` = `_BarTopY()`) -- the portion hidden behind the bar isn't clickable, since visually nothing of hers is there to click on.

**Checked `oUnitControl/Step_0.gml`'s restriction gate for a double-consumption risk** (a click advancing the bubble also being read, same frame, by the blueprint-drag-start check a few lines later) -- confirmed NOT an issue: both `_BubbleRect()` and `_BoogerRect()` bottom out at `_BarTopY()` (~800px range at the current bar art/scale), while the blueprint panel's own rect starts at `BLUEPRINT_UI_ORIGIN_Y = 824` (`BlueprintScripts.gml`) -- the two never overlap, by virtue of the bar's own top edge already sitting above the panel that's drawn ON the bar. No "consumed click" guard was added; flag if the bar/panel geometry ever changes such that this margin closes.

### Mirror interlude (2026-08-13, phase 3 only)

Per request: partway through phase 3, Booger disappears, reappears MIRRORED (opposite side of the screen, facing the opposite direction, speech bubble mirrored too), delivers one line there, then disappears again and reappears back at her normal spot for the closing line.

**A step can carry an optional `transition: "mirror" | "unmirror"` field.** `_UpdateBubble()`'s click-advance logic PEEKS `_steps[scriptIndex + 1]` (the step about to be shown) before actually advancing; if it has a `transition`, instead of calling `_AdvanceScript()` immediately, it sets `pendingMirrorTransition` ("toMirrored"/"toNormal") and calls `Hide()` -- deliberately WITHOUT incrementing `scriptIndex` yet. `Update()`'s "disappearing" case, once she's confirmed fully hidden, checks `pendingMirrorTransition` (before the existing `pendingPhaseAdvance` check): flips `mirrored` accordingly, clears the pending flag, sets `pendingScriptStart = true`, and calls `Show()` again. This deliberately REUSES the exact same `pendingScriptStart` -> landing -> `_AdvanceScript()` machinery the very first phase start already uses to reveal a line only once she's fully risen -- `_AdvanceScript()` increments `scriptIndex` at that point, which is what finally reveals the transition step's own text. No new reveal mechanism was written for this.

**Geometry -- `mirrored` (bool) drives every position/draw helper via three small branches, rather than duplicating each function:**

- `_AnchorX()` -- `TUTORIAL_GUIDE_MIRROR_X` while mirrored, `TUTORIAL_GUIDE_X` otherwise. `TUTORIAL_GUIDE_MIRROR_X` is solved (same "derived macro, not a literal" pattern as `TUTORIAL_GUIDE_X`) so `_VisualCenterX()` lands on the MIRROR of `TUTORIAL_GUIDE_SCREEN_FRACTION_X` (1/5 at the default 4/5) -- a true mirror image of her normal position, not an arbitrary second spot.
- `_DrawXScale()` -- positive (natural/unflipped) while mirrored, negative (flipped) otherwise. `sBoogerPortrait` has a bottom-LEFT origin; normally flipping it (negative xscale) makes it extend LEFTWARD from a right-side anchor (facing screen-center from the right). Mirrored, drawing it UNFLIPPED (positive xscale) from a left-side anchor makes it extend RIGHTWARD instead (facing screen-center from the left) -- position and facing direction reverse together, which is what makes it read as a genuine mirror image rather than just "the same pose moved to the other side."
- `_VisualCenterX()` -- unchanged in shape, already branched on `mirrored` before this phase existed (added defensively when `_AnchorX()`/`_DrawXScale()` were introduced): `_AnchorX() + halfWidth` while mirrored (anchor is the left edge, sprite extends right), `_AnchorX() - halfWidth` otherwise (anchor is the right edge, sprite extends left). Hands (`sBoogerHands`) are drawn at `_VisualCenterX()` unconditionally, same as always -- per request ("make the hands still align to the center of the sprite with the flip") this needed no separate branch, since `_VisualCenterX()` already accounts for the mirror.

`_BoogerRect()`/`_BubbleRect()`/`Draw_Bubble()` (renamed from `_DrawBubble()`, 2026-08-14 -- see Speech bubble below) all branch the same way (mirrored: anchor = left edge, extends right; normal: anchor = right edge, extends left) so the click-hit-test geometry, the bubble's screen-side (right of her normal position, LEFT of her mirrored position -- "mirroring the text box" per request), and the actual draw calls all stay in lockstep, same "single source of geometry" discipline `_BubbleRect()` already established pre-mirror.

**`handsFrame` (int, default 0) -- "switch her hand sprite to index 1" on landing mirrored, back to 0 before disappearing to unmirror.** `Update()`'s "appearing" case sets `handsFrame = 1` the instant she lands (`state = "idle"`) IF `mirrored` is true -- this only ever fires right after the toMirrored landing, since `mirrored` is defensively reset to `false` at the start of every phase (`_StartNextPhase()`) and every OTHER `Show()` in the game happens with `mirrored` already `false`. The reset back to `handsFrame = 0` happens explicitly in `_UpdateBubble()`'s `"unmirror"` branch, BEFORE `Hide()` is called -- per request ("have booger's hands switch back to index 0, THEN disappear"), not on the later landing.

**`mirrored`/`handsFrame` are both defensively reset (`false`/`0`) at the top of `_StartNextPhase()`** -- no phase relies on carrying a mirror state into it from a previous phase; this is purely a safety net, not exercised by the current script (phase 3 is the only phase that ever sets `mirrored = true`, and it always unmirrors before its own last line).

## Player action restriction

`restrictionActive` (bool) + `allowedBuildingTypes` (array -- what `TryPlaceBlueprint`'s gate accepts as a valid TYPE for the whole phase; `[oWaterPump]` phase 0, `[oWheatField, oSawmill]` phase 1, `[oPeasantWard]` phase 2) + `remainingRequiredTypes` (array -- an independent COPY of that phase's `allowedBuildingTypes`, whittled down as each required type gets its first successful placement) + `requireInside` (bool, 2026-08-13, phase 2's Peasant Ward request -- see below) + `trainingRequirements` (array, 2026-08-13, phase 2's "train 2 peasants" request -- see below) are the fields that matter. `allowedBuildingTypes` became an array (2026-08-13, was a single `allowedBuildingType`) specifically because phase 1 accepts both Wheat Field and Sawmill as valid placements -- `TryPlaceBlueprint`'s gate checks `array_contains(...)` instead of `==`, using the same `array_contains()` this project already relies on elsewhere (`AIControl.gml`, `TrainingScripts.gml`, etc.), not a hand-rolled loop. Two enforcement points, unchanged in SHAPE from the original single-phase design (a phase's requirements grew, but the two places that check them didn't move):

1. **`oUnitControl/Step_0.gml`**, a gate checked after the Fate-Engine/pause-menu/Escape gates (in that position specifically so Escape still opens the pause menu during the restriction -- see below) and before the XP-bar-click check. While `restrictionActive`, the ONLY input handled is blueprint drag start/end/cancel (`blueprintController`'s own paging/hover keep working so the player can still SEE the blueprint panel) -- everything else (`orderMenu`, `castleGarrisonMenu`, `armyLimitMenu`, `selectionController`, training-building clicks, the XP bar/Fate Engine) is skipped via an early `exit`, mirroring the exact "checked first, exit" shape the existing overlay gates already use. **This means training-building clicks are still blocked during phase 2 even after the Peasant Ward is placed and its placement requirement is satisfied** -- see Flag below, this is the same "defense in depth, not the real enforcement" gate as always, just newly relevant since phase 2 is the first phase whose completion actually depends on something happening AFTER a click this gate would otherwise block. **2026-08-14: this gate now ALSO runs `plotHoverController`/`buildingHoverController`/`castleBonusHoverController`/`unitSelectHoverController`'s `.Step()` calls, guarded on `global.tutorialGuide.state != "idle"`** -- per request ("don't block hover displays during the tutorial if Booger isn't speaking"). Before this fix, the gate's early `exit` meant these hover controllers' `.Step()` NEVER ran during ANY restriction, for its entire duration (not just while she was actually talking) -- their `.Draw()` calls in `oUnitControl/Draw_64.gml` run unconditionally regardless of restriction, so the visible symptom was hover cards staying stale/blank the whole time a restriction was active, not just while a bubble was on screen. `state == "idle"` was chosen as the "speaking" condition since that's the ONLY state in which her bubble is actually drawn (`Draw_Bubble()`'s own no-op guard).
2. **`BlueprintScripts.gml`'s `TryPlaceBlueprint`**, gated at the top: while `restrictionActive` (and only for `TEAM.PLAYER` -- the AI is never subject to this, and is separately fully paused by `global.tutorialActive` regardless, see `AIControl.md`), any attempt whose building type ISN'T IN `allowedBuildingTypes`, or whose plot is on the wrong SIDE, is rejected -- same `show_debug_message` + `return false` shape every other rejection in this function already uses. **The plot-side check is now `requireInside ? _plot.inside : !_plot.inside`** (2026-08-13, was hardcoded `!_plot.inside` -- every phase before phase 2 needed outside, so this never needed to branch until the Peasant Ward's INSIDE requirement came along). `_plot != noone` is checked FIRST via `&&` short-circuit before that ternary touches `_plot.inside` -- `noone` has no `.inside` to read, so evaluating the ternary unconditionally would error on a bad plot; this ordering was deliberately preserved from the original code. This is the actual eligibility check (which TYPES/SIDES are placeable at all) -- it does NOT track completion progress; that's `CompleteRestriction()`/`NotifyUnitTrained()`'s job, described next.

**Flag: `oPeasantWard`'s existing `BuildingDefinition` already independently expects to be placed inside (training buildings get their own discount/bonus for it, per `BlueprintScripts.gml`'s `BuildingGetsDiscountOnPlot`) -- `requireInside` here is a SEPARATE, tutorial-only enforcement layered on top, not a discovery of a new rule.** The tutorial gate exists to force a specific plot choice during THIS guided step; the underlying game already treated inside-placement as the economically-correct choice for training buildings regardless of the tutorial.

**Two independent requirement KINDS can now gate a phase's completion, checked by two different callers into a shared `_TryAdvancePhase()`:**

- **Placement** (`CompleteRestriction(_buildingType)`, called from `TryPlaceBlueprint`'s success path, gained the `_buildingType` argument 2026-08-13): looks up `_buildingType` in `remainingRequiredTypes` (`array_get_index`) and removes it if present (silently no-ops if it's not there -- already checked off earlier this phase, or not actually a required type -- safe to call defensively), then defers to `_TryAdvancePhase()`.
- **Unit training** (`NotifyUnitTrained(_team, _unitType)`, new 2026-08-13, called from `TrainingScripts.gml`'s `TrainingSpawnUnit` -- see below): no-ops unless `_team == TEAM.PLAYER` and `restrictionActive`; otherwise finds the first `trainingRequirements` entry matching `_unitType` with `remaining > 0` and decrements it, then defers to `_TryAdvancePhase()`.
- **`_TryAdvancePhase()`** is the single completion check both funnel into: the phase only actually ends once `remainingRequiredTypes` is EMPTY *and* every `trainingRequirements` entry's `remaining` has reached 0 (a no-training-requirement phase trivially passes the second half, same as phases 0/1 always have) *and* (2026-08-14) `scriptDismissed` is true. Once satisfied: clears `restrictionActive`/`allowedBuildingTypes`, then either starts the next queued phase or ends the tutorial -- same "immediately if already hidden, otherwise flag `pendingPhaseAdvance` for `Update()`'s `disappearing` case to pick up" logic this already had before this pass, unchanged.

**Bug fixed 2026-08-14: a phase could complete (and cut Booger's own dialogue short) the instant its LAST required building/unit was placed/trained, even if the player was still mid-script reading an EARLIER line.** Nothing previously stopped a player from placing the required building(s) (or queuing the required training) WHILE she was still delivering lines 1-4 of a 5-line phase -- `restrictionActive` (and therefore `TryPlaceBlueprint`'s eligibility gate) is true from the phase's very first line, not just once the last line is reached. When that happened, `CompleteRestriction()`/`NotifyUnitTrained()` would satisfy `_TryAdvancePhase()`'s requirement checks immediately, which (since `state` was still `"idle"`, not `"hidden"`) called `Hide()` right then -- yanking her off-screen mid-sentence and silently starting the NEXT phase the moment she finished disappearing, with the player never having read (or been forced to sit through) the rest of that phase's script. From the player's side this read as the tutorial "skipping over" the requirement entirely, even though it technically HAD been satisfied (just far too early). **Fixed via the new `scriptDismissed` field** (`false` from `_StartNextPhase()`, set `true` only in `_UpdateBubble()`'s own last-line-click branch, right before that branch's `Hide()`/`_TryAdvancePhase()` calls): `_TryAdvancePhase()` now requires `scriptDismissed` in addition to the requirement checks, so an early placement/training completion is silently accepted (the requirement IS checked off) but the actual phase-completion effects (hiding her, advancing) wait until the player has ALSO clicked through to and past her last line. A player who dismisses first and builds after (the originally-intended flow) sees no change at all -- `scriptDismissed` is already `true` by the time `CompleteRestriction()`/`NotifyUnitTrained()` fires.

**`NotifyUnitTrained`'s hook point and why it's a TEAM-WIDE count, not tied to the specific Peasant Ward instance the player just placed.** Per the request ("train 2 peasants from it") a stricter reading would track the exact Ward instance. `TrainingScripts.gml`'s training system has NO existing per-instance completion tracking anywhere -- `TrainingTypeLimit`/queue counts are already summed across every live building of a team+type, and `TrainingSpawnUnit(_building)`'s only universally-shared post-spawn hook (both the "inside, station-only" and "outside, live unit" branches) is the existing `AnalyticsRecordUnitTrained(_building.team, _building.trainsUnit)` call -- team+type, no instance identity. Threading instance identity through JUST for this tutorial check would mean either passing the Ward's `id` around new tutorial-specific state or comparing against it inside otherwise-generic training code. Given the tutorial only allows ONE Peasant Ward to become buildable during this phase in practice (nothing stops placing a second, but there's no reason to), a team-wide "trained 2 Peasants" count reads as functionally identical to "2 from this Ward" in the vast majority of playthroughs -- kept as the simpler, less invasive hook. Flag if strict per-instance tracking is actually wanted.

**Why `remainingRequiredTypes`/`trainingRequirements` are genuine COPIES, never aliases of the phase definition's own arrays/structs** -- `_StartNextPhase()` builds both via explicit element-by-element loops (for `trainingRequirements`, each loop iteration also builds a FRESH `{ unitType, remaining }` struct, not a reference to the phase data's `{ unitType, count }` struct) rather than direct assignment, specifically because GML arrays (and structs referenced by them) are reference types: aliasing would mean mutating the "in progress" copy ALSO mutates the phase's own static definition, corrupting it for the rest of the phase (or, since `scriptPhases` is only built once at `StartIntroScript()`, effectively permanently). Same shared-array hazard `oMatchControl/Create_0.gml`'s `global.blueprints`/`global.resources` comments already call out elsewhere in this project (their fix is the same shape -- fresh literals/copies, never a shared reference two different owners might mutate independently).

**Flag: Escape/pause is deliberately EXEMPTED from the restriction, not literally "the only action."** Blocking Escape too would leave a player with zero way to quit or open Settings mid-tutorial if they wanted to -- judged as an unintended trap rather than the actual intent, so Escape's existing gate was left ahead of (unaffected by) the new one. If literal enforcement (no exceptions at all) was actually wanted, move the guided-tutorial gate above the Escape check instead.

**`oUnitControl/Step_0.gml`'s restriction gate now also exempts training-building clicks, not just blueprint dragging (2026-08-13 fix, surfaced by phase 2).** Every earlier phase only ever needed the PLACEMENT action itself, so the gate's early `exit` never had to let anything else through -- but phase 2's completion depends on actually queuing 2 peasants AFTER the Ward is placed, and `TrainingTryQueueUnit` is normally only reachable from a click-handling block deep inside the UNRESTRICTED body of Step_0 (past the tutorial gate's `exit`, `oUnitControl/Step_0.gml` line ~150 region, per `TrainingScripts.md`) -- meaning without this fix, the player could place the Ward but then have literally no way to click it and start training, since the whole rest of Step_0 never runs during a restriction. Fixed by mirroring the unrestricted block's own "plot, then training building, then blueprint drag" click-priority ordering, trimmed down to just training+drag (plots/walls/army-limit-icon aren't reachable actions during any restricted phase, so they weren't added): inside the `restrictionActive` block, a left-click now checks `instance_position(mouse_x, mouse_y, oTrainingBuildingParent)` first and calls `TrainingTryQueueUnit` if it hits one owned by the player, falling through to the existing `blueprintController.TryBeginDrag()` otherwise. This was caught and fixed proactively while writing this doc section, not requested explicitly -- flagging clearly since it touches the load-bearing restriction gate.

**Bug (2026-08-14, caught via an actual in-engine crash on match start, not statically): every OPTIONAL per-phase/per-step struct key (`requireInside`, `trainingRequirements`, `transition`) must be read via GML's safe struct accessor (`_phase[$ "requireInside"]`), never plain dot notation (`_phase.requireInside`).** GML struct dot-access THROWS `Variable ... not set before reading it` when the struct LITERAL never declared that key at all -- this is a hard error, not the same thing as the key existing with an `undefined` value. `requireInside`/`trainingRequirements` are only declared on phase 2's (Peasant Ward) literal; phases 0/1/3 omit them entirely. `transition` is only declared on phase 3's two mirror steps; every other step (across all 4 phases) omits it entirely. The original `(_phase.requireInside != undefined) ? _phase.requireInside : false` pattern assumed a missing key silently reads as `undefined`, which is true for GML's own loosely-typed VARIABLES but not for struct MEMBERS accessed by name that were never assigned -- crashed the game on the very first `StartIntroScript()` call (phase 0), since phase 0's literal has neither key. Fixed by switching all three reads to the `[$ "key"]` accessor, which DOES return `undefined` for a missing key instead of throwing. **Any future optional per-phase/per-step field must use this same accessor pattern, not dot notation, or it will reproduce this exact crash.**

**Flag: a disallowed blueprint drag during either phase just silently fails to place (debug-message only), no player-facing feedback.** Matches this codebase's existing failure-handling convention everywhere else in `TryPlaceBlueprint` (an unaffordable attempt behaves identically) -- not treated as a gap introduced by this feature, but worth knowing if a clearer in-HUD rejection cue is wanted later.

## 2026-08-15 bugfix pass

Five fixes from one user-reported batch, covered here (the Dealer-specific ones are in `DealerIntroScripts.md`):

**1. Phase 1 (Wheat Field/Sawmill) could complete without either building placed.** Root cause: `_TryAdvancePhase()`'s success branch set `pendingPhaseAdvance = true` UNCONDITIONALLY before branching on `state`, but only the DEFERRED branch (`state != "hidden"`, needs `Update()`'s "disappearing" case to consume it later) actually needed that flag -- the IMMEDIATE branch (`state == "hidden"`, calls `_StartNextPhase()` right there) never cleared it. So after any transition that happened to fire via the immediate branch (routine -- happens whenever the player dismisses a phase's last line before placing its required building, which is the common case), `pendingPhaseAdvance` stayed stale-`true` forever after. The NEXT phase's own eventual `Hide()` (its own last-line dismiss, regardless of whether THAT phase's requirements were actually met) would then be misread by `Update()`'s "disappearing" case as a still-pending advance from the OLD transition, firing `_StartNextPhase()` early and completely bypassing the new phase's `remainingRequiredTypes`/`trainingRequirements` gate. This is exactly what let a player reach the Peasant Ward phase without having placed the Wheat Field/Sawmill. **Fix:** `pendingPhaseAdvance = true` moved inside the deferred (`else`) branch only -- see `_TryAdvancePhase()`.

**2. Resource icons in the "3 W's" line were tinted by the following resource-name color tag.** `{ResourceIconTag("water")}[{TUTORIAL_RESOURCE_WATER_COLOR_TAG}]Water[/c]` -- the icon tag sits immediately adjacent (zero characters between) to the following color-open tag, and Scribble's inline-sprite icons are apparently tinted by whatever color state is active at their position, same rendering path as glyphs. Rather than digging further into Scribble's exact tag-adjacency parsing, each icon is now defensively wrapped in its own explicit `[c_white]...[/c]` scope (white = multiplicative identity, i.e. the sprite's own natural, un-tinted colors) so it can never inherit the immediately-following tag's color regardless of the exact mechanism. See Script content above (the "3 W's" resource line).

**3. Mirrored speech bubble's text sat at the wrong X offset.** `sSpeechBubbleInGame` has a tail baked asymmetrically into its art (not centered in its own drawing space), so the plain `TUTORIAL_BUBBLE_BUFFER`-derived text offset (correct for the DEFAULT/non-mirrored layout) read off-center once mirrored. `Draw_Bubble()` now branches: mirrored uses the new `TUTORIAL_BUBBLE_MIRRORED_TEXT_OFFSET_X` (26, non-mirrored is unchanged). **2026-08-15 follow-up correction: confirmed native-sprite-space, scaled by `TUTORIAL_GUIDE_SCALE` at the point of use -- same convention as `TUTORIAL_BUBBLE_BUFFER` right next to it in the macro block.** The original pass had flagged this as a judgment call and guessed literal GUI px instead; that guess was wrong. Wrap width (set at `Say()` time) is untouched either way.

**4. Hover cards froze on screen instead of fading when a tutorial character popped up.** See `PlotHoverScripts.md`'s Suppression section (`TutorialCharacterSpeaking()`) for the root cause/fix -- summarized: `oUnitControl/Step_0.gml` used to SKIP the hover controllers' `Step()` calls entirely while Booger was idle-talking (and, separately, for the Dealer scene's whole suppression window), which froze whatever a card was already showing instead of letting its own dwell/fade logic ease it away. Both call sites in `Step_0.gml` now call `Step()` unconditionally, and a new suppression check (consulting `global.tutorialGuide.state`/`global.dealerIntro.IsSuppressingInput()`) makes the cards fade out gracefully instead.

**5. Typewriter (and, for Booger, her voice blips) kept running well after the visible text had already finished.** Root cause: `typewriterDone`/the blip system's char lookup were both measured against `string_length(bubbleRawText)` -- the RAW string as passed to `Say()`, including any `[wave]`/`[shake]`/`[c_tag]` Scribble markup. Scribble's own rendering only ever reveals the VISIBLE glyph count (tags parsed out, not counted), which is smaller than the raw length whenever a line has any tag at all -- so `bubbleRevealChars` kept climbing (and blips kept firing, indexed into the wrong string besides) for however many extra "tag characters" the raw string had, well after the actual text was already fully on screen, and the player couldn't click to advance until that extra time elapsed too. **Fix:** `Say()` now calls `.allow_text_getter()` on the built `bubbleText` element and caches `bubbleText.get_text()` (Scribble's own tag-stripped text) as a new field, `bubbleVisibleText` -- both the completion bound and the blip char-lookup now measure against THIS, not `bubbleRawText`. `bubbleRawText` itself is unchanged/still kept (now documented as "for reference" only).

**2026-08-30 follow-up: blip volume cut to 10%.** Booger's blip gain in `_UpdateBubble()` now multiplies in `DIALOGUE_TEXT_BLIP_GAIN_SCALE` (0.1, `DialogueOverlayScripts.gml`) on top of the existing Settings SFX slider/mute -- reused rather than redefined, so this file and `DialogueOverlayScripts.gml`'s own blip stay in sync off one macro. See `DialogueOverlayScripts.md`'s Pitch variation + SFX volume section for the full rationale; this file's blip logic remains a hand-rolled duplicate of that one, not a shared function.

**Typewriter skip (2026-08-15 request, bundled with fix #5 above since both touch `_UpdateBubble()`).** While the typewriter is still running, clicking the bubble/Booger OR pressing space now completes the reveal instantly (`bubbleRevealChars = string_length(bubbleVisibleText); typewriterDone = true;`) and `return`s immediately -- deliberately WITHOUT falling through to the post-typewriter advance-click handling in the same call. This guards against the same press ALSO registering as "advance to next line" in the same frame: `mouse_check_button_pressed()`/`keyboard_check_pressed()` are only true for the exact frame of the press, so by the time `_UpdateBubble()` runs again next frame with `typewriterDone` now true, that same press is no longer "pressed" -- the player has to click/press again to actually advance.
