# DealerIntroScripts

2026-08-14 request: "Now for continuing the tutorial... [Dealer ambush intro to the Fate Engine, full scripted scene]... After that allow the player to interact with the fate engine." `DealerIntroScene()` is a single **global** struct (`global.dealerIntro`, created unconditionally in `oMatchControl/Create_0.gml`, same "always exists, only ever armed conditionally" pattern `global.tutorialGuide` already established) -- armed via `BeginWait()`, called from `TutorialGuideScripts.gml`'s `_TryAdvancePhase()` the instant Booger's own guided tutorial finishes (see `TutorialGuideScripts.md`'s "Dealer-intro hand-off" section).

## Scene structure -- six phases, one linear script array

`phase` moves through `"inactive" -> "waiting" -> "portraitIntro" -> "backgroundReveal" -> "portraitReturn" -> "machineReveal" -> "machineDialogue" -> "awaitingFirstSpin" -> "machineDialogue" (again) -> "done"` (the `"awaitingFirstSpin"` detour, 2026-08-15, only exists between the original ambush script and the post-first-spin follow-up script -- see "2026-08-15 (round 2)" below). `scriptSteps` is one flat array of `{ text, transition, grantToken }` played straight through by `scriptIndex`, regardless of which phase is currently showing it -- there's no per-phase sub-array (unlike `TutorialGuideScripts.gml`'s `scriptPhases`, which resets `scriptIndex` per phase); phase transitions here are just checkpoints along one continuous line count, driven entirely by the `transition` field on the step about to be shown.

**`transition` placement mirrors Booger's own mirror-interlude convention exactly** (`TutorialGuideScripts.gml`'s phase 3, `"mirror"`/`"unmirror"`): the field lives on the step that should be preceded by the transition, not the step that triggers it, and is consumed via a one-step lookahead (`_UpdateBubble()` peeks `scriptSteps[scriptIndex + 1]` before deciding whether to just `_AdvanceScript()` or instead `HidePortrait()` + stash `pendingAfterHide`). Three transition values now exist:

- `"toBackground"` (on the "Hey Kid." step) -- fires after "Come into the woods with me." is dismissed. Calls `fateEngineOverlay.Open(..., true)` (the new `_holdMachine` param, see `FateEngineOverlayScripts.md`'s "Machine hold/release" section) -- the gradient/trees background animates in normally, but the drums/body/lever/Dealer group stays fully withheld off-screen. `phase` becomes `"backgroundReveal"`, which just watches `_GradientProgress()` until it hits 1, then moves to `"portraitReturn"` and calls `ShowPortrait()` again -- literally the SAME portrait, re-shown, now with the Fate Engine's background visible behind her. Per request: "bring in the fate engine screen background, but wait to bring in the fate engine itself, then have her reappear." Consumed in `_UpdatePortraitArch()`'s `"disappearing"` case once she's confirmed fully hidden.
- `"toMachine"` (on the "[wave]TA-DA!!!!![/wave]" step) -- fires after "OH WAIT! THERE IS!" is dismissed. Calls `fateEngineOverlay.ReleaseMachine()` (lets the withheld machine pop up on its own independent timer) and sets `phase = "machineReveal"`, which watches `_MachineProgress()` until it hits 1, then flips to `"machineDialogue"` (`usingMachineBubble = true`) and reveals "TA-DA!!!!!" itself -- the machine finishes popping up BEFORE that line's text appears, so the "reveal" reads as her gesturing at an already-materialized machine, not narrating over an still-animating one. Consumed in `_UpdatePortraitArch()`'s `"disappearing"` case.
- `"awaitFirstSpin"` (2026-08-15, on the "Oooooh nice! It didn't kill you immediately!" step) -- fires after "Just insert the token and pull the lever..." is dismissed. Unlike the two above, this does NOT touch the portrait/`HidePortrait()` at all -- see "2026-08-15 (round 2)" below for the full mechanism.

**Every other step** (no `transition` field, the `[$ "transition"]` accessor -- see below -- reads `undefined`) just calls `_AdvanceScript()` directly on click, same as any normal dialogue line.

**`[$ "transition"]`/`[$ "grantToken"]` -- the safe struct accessor, not dot notation.** Same hazard `TutorialGuideScripts.gml`'s own `requireInside`/`trainingRequirements`/`transition` reads already guard against (documented at length in `TutorialGuideScripts.md`'s "Bug (2026-08-14...)" entry): most of `scriptSteps`' entries never declare `transition` or `grantToken` at all, and GML struct dot-access THROWS on a genuinely-undeclared key (not the same thing as a key holding `undefined`). `_AdvanceScript()`/`_UpdateBubble()` both use `_step[$ "key"]` throughout for exactly this reason.

## Timed ambush, not a scripted-scene-from-match-start

**`BeginWait()`/`waitTimer` (`DEALER_INTRO_WAIT_STEPS` = 3600, "wait for a minute (in frames)" read literally as 60s @ 60 steps/sec).** `Update()` is called EVERY Step by `oUnitControl/Step_0.gml`, unconditionally, regardless of `phase` -- this is deliberate: the initial 60-second wait must tick DURING otherwise-completely-normal play (the whole point of an "ambush" is that it interrupts the player mid-game, not that it's a loading-screen-style scene that owns the frame from the start). `IsSuppressingInput()` (checked by the caller right after `Update()`, same "gate function returns bool, caller decides to `exit`" shape `fateEngineOverlay.isOpen`/`pauseMenu.isOpen` already use) is explicitly `false` during `"inactive"` and `"waiting"` -- only becomes `true` once the timer expires and her portrait actually starts appearing (`"portraitIntro"` onward), through to `"done"` (also `false` -- once concluded, the player has ordinary interactive control of the now-open Fate Engine, no suppression needed).

**Match freeze is a SEPARATE decision from input suppression, made at the exact moment the wait expires, not at `BeginWait()`.** `savedMatchSpeed`/`global.matchSpeed = 0` and the selection/menu/drag reset all happen inside `Update()`'s `"waiting"` branch, right when `waitTimer` reaches 0 -- not in `BeginWait()` itself, since the whole point of the wait is that normal play (including match speed) continues completely undisturbed for that full minute. This mirrors `FateEngineOverlay.Open()`'s own reset block almost verbatim (same five calls: `Deselect()`, `orderMenu.Close()`, `castleGarrisonMenu.Close()`, `armyLimitMenu.Close()`, `blueprintController.CancelDrag()` if dragging) -- duplicated here rather than factored out, since `FateEngineOverlay.Open()` itself doesn't fire until well INTO this scene (the `"toBackground"` transition), and this reset needs to happen the moment she first appears, well before that.

**This scene owns the match freeze for its ENTIRE duration, not just while the Fate Engine overlay happens to be open.** `savedMatchSpeed` is captured/restored by THIS struct (in the wait-expiry block and in `_ConcludeScene()` respectively) -- `global.matchSpeed` stays at 0 continuously from the moment her portrait starts rising through the whole six-phase scene, including the stretches where `fateEngineOverlay.isOpen` is false (the entire portrait-only stages A/B/C, before `"toBackground"` ever fires). `FateEngineOverlay.Open()`'s OWN `savedMatchSpeed`/restore logic is never actually exercised during this scene at all -- by the time `Open(..., true)` is called (stage C's `"toBackground"`), `global.matchSpeed` is already 0 (set by this scene), so `Open()` just re-captures/re-sets the same already-zero value, harmlessly. The real, meaningful restore is this struct's own, in `_ConcludeScene()`.

**`sDealerPortrait` (280x450, 2 frames, bottom-left origin `(0, 450)`) -- confirmed pre-existing but completely unreferenced anywhere in the project before this pass.** Distinct from `sDealer` (the FateEngineOverlay's own leaning sprite, 284x474, 8 frames including the blink animation) -- per request, "the dealer character portrait (different from her leaning sprite)". No other asset changes were needed.

**Right-edge-pinned horizontal position (`_AnchorX()` = `display_get_gui_width()`), per request ("aligning the right hand side of her sprite with the right hand side of the screen").** She's drawn with NEGATIVE xscale (`-DEALER_INTRO_SCALE`) -- since her origin is bottom-LEFT, a flipped draw at exactly `guiWidth` makes her sprite's (post-flip) right edge land exactly on the screen's own right edge, the same "flip a bottom-left-origin sprite to make it read as right-anchored" mechanism `TutorialGuideScripts.gml`'s own default (non-mirrored) Booger placement already uses (`_DrawXScale()`/`TUTORIAL_GUIDE_X`, `TutorialGuideScripts.md`'s "Booger's HUD presence" section). **The facing DIRECTION (flipped/facing-left, vs. drawing her unflipped/facing-right) wasn't specified by the request** -- flipped was chosen so she visually faces INTO the screen/toward the game world, matching the same "faces toward center" convention Booger's own default position uses. Flag if she should instead face outward/off-screen.

**Vertical arch (appear/disappear rise-and-settle) is a byte-for-byte duplicate of `TutorialGuideScripts.gml`'s own `_AnimCurveY()`/`_RiseFraction()`/`_StartY()`/`_OvershootY()`/`_RestY()`, substituting `sDealerPortrait`/`DEALER_INTRO_*` macros for `sBoogerPortrait`/`TUTORIAL_GUIDE_*` ones -- same literal magnitude values throughout (165/128/48/40px, 0.45s/0.22s legs), per request ("her appear and disappear will animate the same as booger's character portrait does").** Deliberately duplicated rather than factored into a shared function -- `TutorialGuide` and `DealerIntroScene` are separate structs with no common base, same "duplicate rather than touch already-working code in an unrelated system" reasoning `TutorialGuideScripts.md`'s own Speech-bubble section already documents for its own typewriter/blip logic relative to `DialogueOverlayScripts.gml`.

**Two-frame "one unit, split across the UI bar" draw (`Draw_Behind()`/`Draw_Front()`), per request: "Use her last frame as a 'draw over the ui bar' and her first frame as a 'draw under the ui bar', but have them move as one unit."** Both calls draw at the IDENTICAL `(x, y)` = `(_AnchorX(), portraitY)` -- only the call SITE differs (before vs. after the bar sprites in `oUnitControl/Draw_64.gml`), which is what actually produces the "layered, moving together" effect: frame 0 (bottom layer, drawn first) reads as "beneath/behind the bar" wherever the bar's own opaque art overlaps her sprite's lower portion, while frame 1 (drawn later, same position) reads as "above/in front of the bar" for that same overlapping region -- both frames still fully overlap and share one single `portraitY`, so there's no separate offset or second position to keep in sync, exactly "move as one unit." **`Draw_Behind()` sits in `oUnitControl/Draw_64.gml` AFTER `fateEngineOverlay.Draw()`** (not before it, unlike `TutorialGuideScripts.gml`'s own Draw_Behind(), which IS first) -- so her portrait renders on top of the Fate Engine's own background reveal during stage C ("bring in the fate engine screen background... then have her reappear" -- she needs to visibly be standing in front of that background once it's up, not underneath it).

## Concluding the scene

**`_ConcludeScene()` (fired by a click on the scene's LAST line, "Just insert the token and pull the lever...") does three things:** restores `global.matchSpeed` from `savedMatchSpeed` (ending the match freeze this scene has held since the portrait first appeared -- see "Timed ambush" above), clears `global.tutorialGuide.fateEngineLocked` (the FIRST code path ever to do so -- see `TutorialGuideScripts.md`'s "Fate Engine lock" section, previously flagged as having no unlock path at all), and calls `fateEngineOverlay.UnlockInteraction()` (clears `interactionLocked`, letting the buttons/lever actually respond to clicks -- see `FateEngineOverlayScripts.md`'s "Machine hold/release + interaction lock" section). **The overlay itself is deliberately left OPEN** -- per request, "after that allow the player to interact with the fate engine," read as a direct hand-off into normal play, not a close-then-reopen. Once `_ConcludeScene()` fires, `phase = "done"`, `IsSuppressingInput()` returns `false`, and `oUnitControl/Step_0.gml`'s OWN pre-existing `if (fateEngineOverlay.isOpen) { fateEngineOverlay.Update(); exit; }` gate becomes reachable again for the first time since the scene began -- from this point on, the player is interacting with an entirely ordinary, already-open Fate Engine session, same as if they'd clicked the XP bar themselves.

## 2026-08-15 bugfix/follow-up pass

**Game froze permanently after the Fate Engine closed, post-spin.** Root cause: the `"toBackground"` transition (`_UpdatePortraitArch()`) calls `fateEngineOverlay.Open(..., true)` while `global.matchSpeed` is ALREADY 0 -- this scene forced it to 0 back at the wait-expiry, well before that `Open()` call. `FateEngineOverlay.Open()`'s own `savedMatchSpeed = global.matchSpeed;` therefore captured 0, not the real pre-ambush speed. That overlay session stays open continuously through the rest of the scene AND into the player's first real, interactive session (spin/cashout/leave) -- `Open()` is never called again to correct the bad capture. So the FIRST time the player actually clicks Leave and the close animation finishes, `FateEngineOverlayScripts.gml`'s `Update()` runs `global.matchSpeed = savedMatchSpeed;` using that stale 0 -- freezing the match permanently, since nothing else ever restores it from there. **Fixed in `_ConcludeScene()`**: immediately after restoring `global.matchSpeed` to this scene's own (correct) `savedMatchSpeed`, it also resyncs `_fateEngineOverlay.savedMatchSpeed` to that same just-restored value -- the minimal, single-point fix, since by that moment we know the TRUE correct value and can just overwrite the overlay's bad one. Doesn't touch `FateEngineOverlayScripts.gml`'s own `Open()`/`Leave()`/`Update()` at all, so every other caller (the ordinary XP-bar click, which never hits this 0-capture case since `global.matchSpeed` is always a genuine 1/2/3 at that point) is unaffected.

**Arm depth-sort during appear/disappear (request).** Per request: her "arm" (frame 1, normally drawn OVER the UI bar by `Draw_Front()`) should draw BEHIND the bar instead during appearing's upswing and disappearing's downswing -- both read as "while she's still in transit through the bar, not yet resting on it." New `_ArmBehindBar()` maps this onto the SAME curve-leg split `_AnimCurveY()` already uses (`_RiseFraction()`'s start<->overshoot leg, the LONG leg of the arch): appearing checks it on the way up (`_t <= _RiseFraction()`), disappearing checks it on the way down (`1 - _t <= _RiseFraction()`, since disappearing samples the curve backward). True only during the long transit leg, in EITHER direction -- false during the short overshoot<->rest settle leg, and false while idle/hidden (arm draws normally, in front, the rest of the time). `Draw_Behind()` now draws frame 1 too (in addition to frame 0) whenever `_ArmBehindBar()` is true; `Draw_Front()` no-ops in that case to avoid a double-draw.

**Bubble repositioning (request).** Both bubble-rect functions gained a fixed nudge, applied on top of their existing geometry: `_PortraitBubbleRect()` (UI-bar stage) shifts `DEALER_INTRO_PORTRAIT_BUBBLE_SHIFT_X` (-160, left) into its `_bx` calculation; `_MachineBubbleRect()` (Fate-Engine stage) shifts `DEALER_INTRO_MACHINE_BUBBLE_SHIFT_X`/`_Y` (+96 right, -32 up) into its `_bx`/`_bottomY`. **2026-08-15 follow-up correction: the FATE-ENGINE/machine-stage shift is native-sprite-space, scaled by `DEALER_INTRO_SCALE` at the point of use -- matching `sSpeechBubbleInGame`'s own `DEALER_INTRO_SCALE`-scaled draw in that same function.** The original pass had guessed literal GUI px for both shifts; that guess was confirmed wrong specifically for the machine-stage one. The UI-bar/portrait-stage shift was NOT called out in the follow-up and stays a literal GUI px -- flag if it should match too, for consistency. `DEALER_INTRO_MACHINE_BUBBLE_BOTTOM_OFFSET_Y` (the pre-existing anchor this shift is added to) also stays unscaled/literal, unchanged from before -- not covered by the follow-up either, so now technically an inconsistent mix within the same calculation; flag if it should be corrected to match.

**Typewriter skip + visible-text-length fix (same root cause/fix as `TutorialGuideScripts.gml`'s matching pass, see that file's `.md`).** `Say()` now calls `.allow_text_getter()` and caches `bubbleText.get_text()` (Scribble's own tag-stripped text) as `bubbleVisibleText` -- the typewriter's completion bound now measures against THIS instead of `bubbleRawText`'s raw (tag-included) length, so lines carrying `[wave]`/`[shake]`/color-tag markup (several of `scriptSteps`' lines do) no longer take noticeably longer to finish than their visible text actually needs. `_UpdateBubble()` also gained the same click-or-space skip-to-end (checked against the current stage's bubble/sprite rect, whichever is active) with the same "return immediately, don't also advance this frame" guard -- see `TutorialGuideScripts.md` for the full guard reasoning, identical here.

**`IsSuppressingInput()` now also returns `false` during `"awaitingFirstSpin"`** (alongside `"inactive"`/`"waiting"`/`"done"`) -- this is the mechanism that actually lets the player interact with the Fate Engine during this window: `oUnitControl/Step_0.gml`'s own Dealer-scene gate no longer exits early, so execution falls through to its ALREADY-EXISTING `if (fateEngineOverlay.isOpen) { fateEngineOverlay.Update(); exit; }` gate -- ordinary, unmodified Fate Engine session behavior (buttons/lever respond, other input stays blocked by the overlay itself, exactly as if the player had opened it fresh via the XP bar). **`Update()`'s own `if (_fateEngineOverlay.isOpen) _fateEngineOverlay.Update();` call was correspondingly gated on `IsSuppressingInput()` too** -- without this, the overlay would get `Update()`'d TWICE per Step during `"awaitingFirstSpin"` (once here, once via Step_0.gml's own now-reachable gate), double-ticking its internal timers/animations. No changes were needed to `oUnitControl/Step_0.gml` itself -- its existing gate ordering already does the right thing once `IsSuppressingInput()` reports `false` for this phase.

**`LockInteraction()` (new, `FateEngineOverlayScripts.gml`) -- the inverse of the existing `UnlockInteraction()`.** Added specifically so this second freeze/lock window doesn't need a fresh `Open()`/hold cycle -- just flips `interactionLocked` back to `true` on the already-open overlay. See `FateEngineOverlayScripts.md`.

**Why "first spin LANDING" rather than "first spin STARTED" or "first cashout."** The new dialogue's opening line ("It didn't kill you immediately!") reads as a reaction to an already-resolved outcome, not to the act of pulling the lever itself -- and the request's own framing ("After the player spins the lever the first time... the dealer says this") pins the trigger to the spin itself, with the lock-in/cashout mechanics only being EXPLAINED afterward in the dialogue, not gating when it starts. A player could therefore hear this monologue having only spun once and not yet touched Cash Out -- intentional per this reading.
