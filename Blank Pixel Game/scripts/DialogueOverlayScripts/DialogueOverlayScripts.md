# DialogueOverlayScripts

The dialogue box system: `DialogueOverlay` struct (speaker name/text + up to `DIALOGUE_MAX_OPTIONS` response options, hover/click handling, drawing). First wired up by the Hub Town's Beggar tutorial dialogue (`HubTownMenuScripts.gml`).

## Assets

`folders/In Game/UI/Assets/Dialogue.yy`:

- `sDialogueUIBack` -- box background, 374x346 native, 4 frames. Frame index = `optionCount - 1` (`DialogueBoxFrame()`).
- `sDialogueUIOptionA/B/C/D` -- one option-row sprite per POSITION (A = 1st option, etc.), not per option-count. 328x25 native each, 2 frames each (0 = not hovered, 1 = hovered).
- `sDialogueUIExit` -- 13x14, 2 frames. Right-aligned with the box's right edge, its own bottom edge flush against the box's top edge (no gap -- no exact offset was specified). Gated by `exitEnabled`.

## Layout & scale

Shipped at native (1x) size; numbers were internally self-consistent only at 1x (`DIALOGUE_OPTION_START_X` (15) + option sprite width (328) + 31 == box width (374); same 31px margin falls out of the height math too -- strong signal the art was drawn for exactly 1x).

2026-08-06: scaled to `DIALOGUE_SCALE = 2`. Every position/offset macro (`DIALOGUE_NAME_TEXT_X/Y`, `DIALOGUE_SPEAKER_TEXT_X/Y/WRAP_W`, `DIALOGUE_OPTION_START_X/Y`, `DIALOGUE_OPTION_TEXT_OFFSET_X/Y`) stays at its native value; every use site multiplies by `DIALOGUE_SCALE`. `sprite_get_width()`/`height()` always return native dimensions regardless of draw-time scale, so layout/hit-test math built on them needs the same `* DIALOGUE_SCALE`.

Text stays UNSCALED (no `.scale()` call) -- font size didn't change, only the geometry around it. Wrap widths DO scale (a layout concern, not a font-size one).

`DIALOGUE_OPTION_ROW_GAP` (2px) -- flat final on-screen px between stacked option rows, added after `DIALOGUE_SCALE` is applied to row height, in both `Draw()` and `_HitTestOption()`. Previously zero-gap. Known effect: pushes the last row down `(N-1) x 2px` further than the original margin math assumed (up to 6px at 4 options) -- worth a visual check against the box art's bottom border.

## Text

Reuses `HoverCardScripts.gml`'s established font/color/shadow convention directly: `HOVER_CARD_BODY_FONT`/`HOVER_CARD_TEXT_COLOR`, drawn via `DrawCardTextWithShadow()`. Speaker text wraps to `DIALOGUE_SPEAKER_TEXT_WRAP_W`; each option wraps to its own sprite width minus the text offset (defensive -- not explicitly requested).

**Speaker body text color is its own constant, `DIALOGUE_SPEAKER_TEXT_COLOR`.** First pass (2026-08-10 request: "value... almost black, about 90% black") was `make_color_hsv(0, 0, 26)` -- pure grayscale at ~10% HSV value. Superseded same day by a follow-up request ("bring the hue and saturation to match the option text color, and set the value to 50") -- now `make_color_hsv(color_get_hue(HOVER_CARD_TEXT_COLOR), color_get_saturation(HOVER_CARD_TEXT_COLOR), 50)`, i.e. `HOVER_CARD_TEXT_COLOR`'s own hue (~29/255) and saturation (~62/255) at a fixed 50/255 value -- derived from the macro at reference time rather than hardcoded, so it stays in sync if `HOVER_CARD_TEXT_COLOR` ever changes. A muted, darker version of the same warm tan the rest of the UI uses, rather than a neutral gray. Name text and option text are untouched, still `HOVER_CARD_TEXT_COLOR` -- only the `_speaker` body line changed.

## Fade in/out

2026-08-10 request: fade in on first appearance (together with the background dim), switch instantly between nodes of the same conversation (unchanged from before), fade out on exit.

`isOpen` no longer means "visually present this instant" -- it now means "exists in any capacity, including mid-fade." `closing` (new field) distinguishes "fading out" from "fully open." `alpha` (0..1) drives the background dim (`0.75 * alpha`) and every element's blend alpha (box, name/speaker/option text via `DrawCardTextWithShadow`'s `_alpha` param, option sprites, exit button) uniformly, so everything fades together rather than the box popping in ahead of its own text.

`Close()` doesn't instantly finish anymore -- it sets `closing = true` and leaves `isOpen` alone. `Update()` keeps running (and animating `alpha` toward 0) until the fade completes, at which point it finally sets `isOpen = false`. This is what makes exit fade out: the exit-button branch in `Update()` calls `Close()` then returns, and subsequent Step calls see `closing == true` and animate the fade with input handling skipped entirely (no hover/click while fading out).

`Open()` is what makes node-to-node switching instant despite `Close()` now being "soft": every response-select branch in `Update()` calls `Close()` immediately followed (synchronously, same frame) by `onSelect(...)`, which -- for every dialogue tree in this codebase today -- immediately calls `Open()` again. `Open()` checks `isOpen` (still `true`, since `Close()` never touches it) to tell "already open, just switching" apart from "opening from cold": already-open snaps `alpha` to `1` and clears `closing`, so the fade-out `Close()` just started never gets a chance to actually animate -- it's overwritten within the same frame, before any Draw() call sees it. Cold-open (`isOpen` was `false`) starts `alpha` at `0` so `Update()`'s normal (non-closing) branch fades it up over `DIALOGUE_FADE_STEPS`.

`DIALOGUE_FADE_STEPS = 15` (~1/4 sec at 60fps) -- same step-based `alpha +/-= 1/STEPS` idiom `PLOT_HOVER_FADE_STEPS` uses (`PlotHoverScripts.gml`), just a separate constant since this is a foreground modal fade, not a hover-tooltip fade, and there's no reason to force them to match.

**Side benefit for callers**: anything watching `isOpen` to know when a conversation has truly ended (e.g. `HubControl.Update()`, `HubControlScripts.gml`) now correctly waits for the fade-out to finish rather than firing the instant `Close()` is called -- this wasn't the primary goal of this change but falls out of it naturally.

## Position & portrait

2026-08-13 request: hug the right edge of the screen (32px buffer), and support an optional character portrait hugging the bottom-right corner.

Box `x` changed from centered (`(guiWidth - boxWidth) / 2`) to right-hugged (`guiWidth - boxWidth - DIALOGUE_RIGHT_MARGIN`, `DIALOGUE_RIGHT_MARGIN = 32`). `y` is untouched (still vertically centered) -- only horizontal hugging was requested. `_ExitRect()` derives from the box's `x`/`width` rather than hardcoding a position, so the exit button's top-left-of-box anchoring carries over correctly without a separate edit.

**2026-08-13: superseded.** Right-hugging is gone -- the box now centers within a `DIALOGUE_CENTER_SLOT_WIDTH` (1280px, 2/3 of the nominal 1920 GUI width) horizontal slot. The slot itself is centered on screen (`_slotX1 = (guiWidth - 1280) / 2`), so the box's own center lands on the slot's center, which lands on the screen's center -- algebraically this reduces to just centering the box on the full GUI width, but the code spells out the 1280 slot explicitly (rather than skipping straight to `(guiWidth - boxWidth) / 2`) since that's what was literally requested, and it leaves room to later offset the slot within the screen without touching the box-centering math itself. `DIALOGUE_RIGHT_MARGIN` macro removed (no longer used anywhere).

`portrait` (new field, sprite asset or `undefined`) is passed as `Open()`'s 9th argument and drawn -- when set -- before the box sprite each `Draw()` call, so the box layers on top of/beside it rather than under it. `_PortraitDrawPosition()` anchors bottom-left, screen edge exactly (`x = 0`, `y = guiHeight`, no buffer in either direction) at `DIALOGUE_PORTRAIT_SCALE` (aliased to `DIALOGUE_SCALE`, matching `RulerPortraitScripts.gml`'s existing portrait-scale precedent elsewhere in the project). Uses `sprite_get_xoffset()`/`sprite_get_yoffset()` rather than assuming a specific origin, so it positions correctly regardless of a given portrait sprite's baked-in origin. **2026-08-13: any visual buffer from the screen edges is deliberately NOT handled in this code** -- per explicit request, buffer is instead baked into the portrait sprite's own origin (offsetting the origin inward from the art's edges), so `_PortraitDrawPosition()` stays a flush zero-buffer anchor and each portrait sprite controls its own spacing independently. (Previously had a `DIALOGUE_PORTRAIT_MARGIN_X` 16px macro and right-anchoring; superseded same day -- see Position & portrait history below if this needs to be reverted.) Portrait alpha is tied to the overlay's own fade `alpha`, so it fades in/out with the rest of the box.

**2026-08-13: portrait also slides in horizontally, driven by the same `alpha`.** `_PortraitDrawPosition()` computes `_slideOffset = (1 - alpha) * (portrait's scaled width / 2)` and subtracts it from `x` -- at `alpha = 0` the portrait sits a full half-sprite-width to the left of its resting spot (partially/fully off-screen depending on the sprite), and eases to `0` offset (resting position) as `alpha` reaches `1`. Since `alpha` is the same field driving fade-in AND fade-out, this naturally reverses on exit (slides back left as it fades out) and snaps straight to rest position with no slide on an instant node-to-node switch (`alpha` snaps to `1` in that case) -- consistent with how every other element already behaves around `alpha`, so no new state was needed.

`HubTownMenuScripts.gml`'s six Beggar dialogue `Open()` calls pass `sBeggarPortrait`; `WarRoomMenuScripts.gml`'s Booger stub node passes `sBoogerPortrait` (2026-08-13) -- every other War Room/Connelius node passes no portrait at all (`undefined`), since no Connelius dialogue portrait sprite exists yet. See `WarRoomMenuScripts.md`'s "Booger handoff" section for the current limitation this creates (node-to-node portrait swaps are instant, not a cross-fade -- fine while there's only ever one portrait in play at a time, but a real gap once Connelius gets his own portrait and the two need to visually swap).

## Typewriter (speakerText only)

2026-08-13 request: "update the speaker text to use the typewriter effect." Uses Scribble's built-in `.reveal(_character)` element method (`__scribble_class_element.gml`) -- the same mechanism the vendored `draw_text_scribble_ext()` helper uses for its own `_reveal` param -- rather than hand-rolling a `string_copy()`-based typewriter (which Scribble's own doc comments explicitly discourage: "It is common practice... draw_text_ext(..., string_copy(...)). Instead... draw_text_scribble_ext(...)").

`speakerRevealChars` (real) accumulates via `DIALOGUE_TYPEWRITER_CHARS_PER_SECOND * (delta_time / 1000000)` each `Update()` call (real seconds, not frame count -- same idiom used throughout this pass, e.g. the War Room Continue button's hover pulse) while the overlay is open and not `closing`. Reset to `0` every time `Open()` rebuilds `speakerText` -- covers both a cold open AND a node-to-node switch, so every new line types out fresh rather than continuing some previous line's progress. `Draw()` calls `speakerText.reveal(floor(speakerRevealChars))` right before drawing it; once `speakerRevealChars` exceeds the text's real rendered length, further increments are harmless no-ops (`.reveal()` past the end behaves identically to no limit at all) -- so there was no need to compute/track the string's true visible-character count (which would also have to account for command-tag markup like `[shake]...[/shake]` not counting toward visible length -- Scribble's own reveal system already handles that correctly internally; this codebase doesn't need to duplicate it).

Only `speakerText` types out -- `nameText` and `optionTexts` draw in full immediately, matching the literal request ("update the speaker text"). `DIALOGUE_TYPEWRITER_CHARS_PER_SECOND = 40` is a judgment call, not specified -- tune to taste.

**No skip-ahead/click-to-finish affordance was added.** A player can click a response before `speakerText` finishes typing out (option rows are drawn/clickable independent of typewriter progress) -- not requested either way, flagged below.

## Per-character speaker sound (2026-08-13, second pass)

Request: "Added Speech Sounds for the three speakers we have (Beggar, Booger, and Connelius)" -- `aBeggarSpeak`/`aBoogerSpeak`/`aConneliusSpeak` (`folders/Sounds/Dialogue.yy`), each a very short (~0.09-0.17s) blip clip, not a full voice line. `Open()`'s new `_speakerSound` (10th) argument stores it in `speakerSound`; every dialogue-tree caller in this codebase now passes its speaker's own sound (`HubTownMenuScripts.gml` -> `aBeggarSpeak`, `WarRoomMenuScripts.gml`'s Connelius nodes -> `aConneliusSpeak`, its Booger/Boog nodes -> `aBoogerSpeak`).

**Why a hand-rolled per-character throttle instead of the vendored Typist class.** The clip durations (~100-170ms) are far longer than one typewriter character at `DIALOGUE_TYPEWRITER_CHARS_PER_SECOND = 40` (25ms/char) -- firing a blip on every revealed character would spam heavily overlapping playback. Scribble ships a whole separate `scribble_typist()`/`Typist` class (`__scribble_class_typist.gml`) with its own built-in `sound_per_char()` throttle (`__sound_finish_time = current_time + 1000*audio_sound_length(...) - overlap`) that solves exactly this -- it was seriously considered, but adopting it would mean replacing this file's already-working `.reveal()`-based typewriter with the Typist's own progression/draw API, a much larger change to a shared system than this request asked for. Instead, `Update()` hand-rolls the SAME throttle formula directly:

```
speakerSoundFinishTime = current_time + (1000 * audio_sound_length(speakerSound)) - DIALOGUE_TEXT_BLIP_OVERLAP_MS;
```

reset to `current_time` (i.e. "allowed immediately") every `Open()` call, so each new line's first revealed character can always blip right away. A blip only fires when `floor(speakerRevealChars)` crosses a new integer boundary since the previous frame (a genuinely new character became visible), `current_time >= speakerSoundFinishTime` (previous blip has had roughly its own duration to breathe), and the just-revealed character (looked up via `speakerRawText`, the plain pre-Scribble string cached at `Open()` time) isn't a space or newline. `DIALOGUE_TEXT_BLIP_OVERLAP_MS = 20` is a judgment call (small, mirrors the vendor's own `_overlap` parameter). **Known approximation**: whitespace-skipping and the character lookup index into `speakerRawText` rather than the Scribble-rendered/tag-stripped text, so a line using a command tag (e.g. node L's `[shake]...[/shake]`) may have its blip-eligible character count run very slightly out of sync with the true visible text -- inconsequential in practice since `[shake]` is the only tag currently in use and doesn't meaningfully change indexing near where it appears.

`speakerSound` defaults to `undefined` (no blip) -- every `Open()` call site NOT explicitly updated for this pass (there are none left, but future ones) silently gets no sound rather than an error.

**Pitch variation + SFX volume (2026-08-13, third pass).** Each blip now plays via `audio_play_sound`'s extended `(sound, priority, loop, gain, offset, pitch)` form rather than the bare 3-arg call -- confirmed supported by this project's GameMaker version since the vendored Scribble library's own `__scribble_play_sound()` (`__scribble_play_sound.gml`) already calls it the same way (`SCRIBBLE_AUDIO_PLAY_FUNCTION` = `audio_play_sound`). Pitch is randomized per-blip, `random_range(DIALOGUE_TEXT_BLIP_PITCH_MIN, DIALOGUE_TEXT_BLIP_PITCH_MAX)` = `0.9..1.1` (judgment call -- a ±10% range reads as "talking" without going chipmunk/demonic; tune to taste), so rapid repeated blips of the same short clip don't sound robotically identical.

Gain now ties into the Settings menu's existing SFX slider/mute (`global.gameSettings.sfxVolume`/`sfxMuted`, `SettingsOverlayScripts.gml`) -- `_gain = sfxMuted ? 0 : PerceptualGain(sfxVolume)`, the exact same squared-curve treatment `ApplyGameSettings()` already gives the title music's Music slider. These fields existed before this pass but were "stored/persisted, not applied to anything real yet -- no SFX sound assets exist in the project" (per this doc's own prior note) -- the speaker blips are the first real consumer. Read live at play-time rather than cached/pushed by `ApplyGameSettings()`, since each blip is a fire-and-forget one-shot with no persistent sound instance to update later (unlike the looping title music, which DOES need a live update when the slider moves while music is already playing). Master volume doesn't need separate handling -- `audio_master_gain()` already applies to every sound in the game automatically at the engine level, blips included.

**2026-08-30 follow-up: flat 10% attenuation.** Per explicit request ("lower all the typewriter text sound effects volume to 10% of their current levels"), the blip's final gain is now `(sfxMuted ? 0 : PerceptualGain(sfxVolume)) * DIALOGUE_TEXT_BLIP_GAIN_SCALE`, with the new `DIALOGUE_TEXT_BLIP_GAIN_SCALE = 0.1` macro living alongside the other `DIALOGUE_TEXT_BLIP_*` macros. This is a flat multiplier layered on TOP of the Settings SFX slider/mute, not a replacement for it -- the slider and mute checkbox still scale/silence blips exactly as before, just off a 90%-quieter baseline. `TutorialGuideScripts.gml`'s Booger-blip logic (duplicated, not shared -- see that file's own doc) reuses this same macro rather than defining its own, so the two stay in sync. The Dealer's ambush scene (`DealerIntroScripts.gml`) has no voice-blip sound asset at all (`aDealerSpeak`-equivalent doesn't exist), so there was nothing to scale there.

## Text input -- "signing line" (2026-08-13, second pass)

Added for `WarRoomMenuScripts.gml`'s Booger tree, node K: "instead of a dialogue option, place a Signing Line, which is just a horizontal line the same width as an option... as a typable text box. Below, add an option that says '[Sign]'." No text-input mechanism existed anywhere in this codebase before this (`keyboard_string` was unused project-wide) -- this is the first.

**Shape.** `Open()` gained three new trailing arguments: `_speakerSound` (above), `_textInputEnabled` (bool, default `false`), `_textInputInitialValue` (string, default `""`). When `_textInputEnabled` is true, option row 0's normal sprite+label slot is replaced by a typable line, and the real `_options` array (still passed normally, e.g. `["[Sign]"]`) is drawn starting one row lower -- `_HitTestOption()` and the `Draw()` option loop both add a `DialogueOptionSprite(0)`-sized row offset when `textInputEnabled`, and `DialogueBoxFrame()` is now called with `array_length(options) + (textInputEnabled ? 1 : 0)` so the background box sizes for the extra visual row. The returned option `_index` from a click is unaffected by the offset -- it's still 0-based into the real `options` array, only the on-screen row position shifted.

**Capture mechanism.** Uses GameMaker's built-in `keyboard_string` global directly -- the standard/idiomatic way to build a simple text field, and safe here since nothing else in this project reads or writes it (confirmed via a full-codebase grep before adding this). `Open()` seeds `keyboard_string = _textInputInitialValue` when entering text-input mode (so a caller can re-open the SAME node with a previous attempt preserved -- see `WarRoomMenuScripts.md`'s K/L signing-line loop), and clears it (`keyboard_string = ""`) whenever `Open()` is called WITHOUT text input, or when `Close()` runs while text input was active, so stray typed characters can't leak into a later node. `Update()` copies `keyboard_string` into the public `textInputValue` field every frame while active, after stripping `\n`/`\r`/`\t` (single-line field only) and clamping to `DIALOGUE_TEXT_INPUT_MAX_LENGTH` (20, judgment call) via `string_copy`.

**Rendering.** `textInputText` (a Scribble element, styled like `optionTexts`) is only rebuilt when `textInputValue` actually changes (`__textInputLastRenderedValue` cache) rather than every frame, to avoid needless Scribble object churn during typing. Shows the typed text plus a static `"|"` caret -- **no blink animation**, a deliberate simplicity call (a blinking caret would need its own timer state; static was judged sufficient for a one-off signing field). The line itself is a plain `draw_line_width` call (not a sprite) spanning the option row's width, positioned at the row's bottom edge per the request ("aligned vertically where the bottom of an option would be").

**Reading the result.** `textInputValue` is a public field -- the caller reads `dialogueOverlay.textInputValue` from inside its `onSelect` callback (e.g. `WarRoomMenuScripts.gml`'s `_OnBoogerSign`) to get the signed name. This works because `Close()` (which the generic option-click handler in `Update()` always calls right before invoking `onSelect`) only clears `keyboard_string`, not `textInputValue` itself -- the value survives long enough for the callback to read it.

**Not handled / explicitly out of scope**: no validation beyond the caller's own choice to guard against empty input (see `WarRoomMenuScripts.md`); no IME/non-ASCII input testing; no click-to-focus (the field is always "focused" whenever `textInputEnabled` is true, there's only ever one on screen).

## API

- `DialogueOptionSprite(_index)` → sprite for option position 0..3.
- `DialogueBoxFrame(_optionCount)` → box background frame index.
- `DialogueOverlay()` constructor -- plain struct, owner calls `Update()`/`Draw()` each frame while `isOpen`.
  - `Open(_name, _speaker, _options, _onSelect, _exitEnabled, _onExit, _optionsItalic, _nameColor, _portrait, _speakerSound, _textInputEnabled, _textInputInitialValue)` -- shows the box. Safe to call while already open (replaces content in place). `_name` = "" for no name line. `_onSelect(_index, _text)` fires right before close; `lastSelectedOption`/`lastSelectedText` are also set for pollers. `_onExit()` fires on exit-button click. `_optionsItalic` applies to the whole response set. `_nameColor` defaults to the standard text color. `_portrait` (optional, default `undefined`) -- sprite drawn bottom-right anchored, see Position & portrait below. `_speakerSound` (optional, default `undefined`) -- per-character throttled blip sound, see Per-character speaker sound below. `_textInputEnabled`/`_textInputInitialValue` (optional) -- signing-line text field in option row 0, see Text input below.
  - `Close()`, `SetExitEnabled(_enabled)` -- toggle exit availability without touching anything else.

## Gotcha: literal `[`/`]` in option/speaker text

`_options`/`_speaker`/`_name` strings pass straight into `scribble()`, which treats `[`/`]` as its own command-tag delimiters -- a literal button label like `"[Continue]"` gets parsed as an (unrecognized) tag and renders BLANK, not as the bracket characters. Found 2026-08-10 in `HubTownMenuScripts.gml`'s Beggar tree. Escape a literal opening bracket by doubling it (`"[[Continue]"`); the closing bracket needs no escaping since it's only special while a tag is already open. This isn't specific to the Beggar tree -- any future `DialogueOverlay.Open()` caller with bracketed literal text needs the same escaping.

## Known assumptions / scope limits (flag if wrong)

- No Escape-to-dismiss or click-outside-to-dismiss -- the exit button (when enabled) is the only sanctioned way out without picking a response.
- Position is always centered on screen, not click-anchored.
- Option text wrapping is defensive (not explicitly requested) -- flag if options should instead be assumed always short enough to never wrap.
- Typewriter reveal doesn't gate response clicks -- a player can select an option before `speakerText` finishes typing out (see Typewriter above).
- Node-to-node portrait swaps are instant, not a cross-fade -- only matters once two different dialogue trees' nodes both use portraits back-to-back in the same conversation (see Position & portrait above and `WarRoomMenuScripts.md`'s "Booger handoff" section).
- Per-character speaker blip uses the raw pre-Scribble string for whitespace/length checks, not the tag-stripped rendered text -- see Per-character speaker sound above.
- Signing-line text input has no blink animation, no click-to-focus, and no non-ASCII/IME testing -- see Text input above. Empty-signature handling lives in the CALLER (`WarRoomMenuScripts.gml`'s `_OnBoogerSign`), not in `DialogueOverlay` itself -- this struct will happily report back an empty `textInputValue` if asked.
