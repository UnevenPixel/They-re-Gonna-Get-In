# FateEngineOverlayScripts

The real Fate Engine session overlay: play-area gradient tint + battlefield freeze, an animated tree/machine open-intro AND matching reverse close/leave outro (2026-08-14), the drum machine, a physical pull lever (2026-08-14, replaces the old Spin button), The Dealer (2026-08-14, a character sprite leaning on the machine), and leave/cashout buttons. Replaces the old `oFateEngineDrumTest` visual-only harness (deleted). Opened by clicking the XP bar.

## Behavior while open

- `global.matchSpeed` forced to 0 on `Open()`. **2026-08-14 follow-up:** `Leave()` no longer restores it immediately -- it only starts the close animation (`closing = true`); `global.matchSpeed`/`global.fateEngineOverlayActive` aren't restored/cleared until that animation actually finishes, in `Update()`'s finalization block (see Close/leave animation below). Drums themselves don't read `matchSpeed` (independent UI mechanic).
- Selection cleared, targeting/menus/blueprint-drag all canceled on `Open()`.
- `oUnitControl/Step_0.gml` early-exits every other Step system while open.
- `Draw()` runs first in `oUnitControl/Draw_64.gml` (before the UI bar) so the gradient tint (see Open-intro animation below) sits behind the persistent UI bar.

`Cashout()` grants real rewards via `FateEngineRollReward()` (`FateEngineDrumScripts.gml`) -- built from registered building types + active resources.

**Bug fixed 2026-08-16: re-spinning within an already-active session stacked EVERY past spin's rewards instead of replacing them.** `pendingRewards` was only ever cleared in `Spin()`'s "starting a brand-new session" branch -- every subsequent free re-spin within that same session left it untouched, and `Update()`'s results-landed block (`resultsBanked` flipping true) just kept `array_push()`-ing 3 more entries on top with each landed spin, so a player who spun 4 times before cashing out got 12 items granted, not the 3 actually shown on the tumblers at that moment. Fixed by clearing `pendingRewards = []` immediately before that same push loop, every time results land -- it now always holds exactly one entry per drum, reflecting only the CURRENT tumbler state, regardless of how many times the player has re-spun this session.

## Open-intro animation (2026-08-14 request)

Every `Open()` replays a three-stage intro sequence, driven off a single shared step counter (`introElapsedSteps`, reset to 0 in `Open()`/defensively in `Leave()`, incremented once per `Update()` while open and capped at `_IntroTotalSteps()`). Every stage's actual motion/fade is still a `lerp()` call against a 0..1 progress ratio, per the original request ("smoothly do all of these animations using lerp") -- but as of the 2026-08-14 follow-up ("ease the tree parallax in slower", "have the fate engine popping up also be lerped/eased in"), the RATIO fed into two of those lerps (the trees' parallax position, and the machine's pop-up offset) is no longer the raw linear progress -- it's remapped through `_FateEngineEaseInCubic(_t)` (`_t * _t * _t`) first. This keeps the actual interpolation itself a plain `lerp()` (satisfying the original "using lerp" instruction literally) while shaping ITS INPUT to read as a slow start that accelerates toward the end -- true ease-IN, the mirror image of `TutorialGuideScripts.gml`'s own ease-OUT cubic (`1-(1-t)^3`, "decelerates INTO the peak") used for its arch's rise leg. The gradient tint's own fade (Stage 1) and the trees' fade-in ALPHA (Stage 2) both deliberately stay on the raw linear ratio -- the follow-up request was specifically about the trees' PARALLAX (position) and the machine's pop-up, not the fades.

**Stage 1 -- gradient tint (`DrawGradientTint()`, `_GradientProgress()`).** Fades in (linear) over `FATE_ENGINE_INTRO_GRADIENT_STEPS` (90 steps, ~1.5s -- untuned judgment call, matching the "steps ~= real seconds at room speed" convention `DIALOGUE_FADE_STEPS`/`PLOT_HOVER_FADE_STEPS` already established elsewhere in this project; **2026-08-14 follow-up: was 60 steps, raised x1.5 as part of the "make all of these animations slower by 50%" pass -- see Close/leave animation below**). **Replaces the old flat, uniform 0.75-alpha full-GUI dim rectangle entirely** -- the new `shFateEngineGradientTint` shader (new asset, `shaders/shFateEngineGradientTint/`) renders a diagonal falloff, strongest (alpha = `FATE_ENGINE_GRADIENT_TINT_MAX_ALPHA`, 0.85 -- 2026-08-14 follow-up "make the dimming darker as a whole", raised from the initial 0.6 pass, still untuned) at the top-left corner, fading to 0 at the bottom-right, per request. Scoped to `(0,0)-(guiWidth, bodyBottomY)` -- "everything above the UI bar edge" -- rather than the full GUI height: the old dim's own portion below `bodyBottomY` was ALWAYS invisible anyway (the opaque `sMainUIBarBottom` sprite draws right after and covers it, per the existing "dim sits behind the persistent UI bar" comment), so this is a faithful visual replacement, not a coverage reduction. Tint color is `FATE_ENGINE_GRADIENT_TINT_COLOR` (`make_color_rgb(0x3A, 0x2E, 0x4A)`, matching this overlay's existing button purple -- judgment call). The shader itself only ever operates on a plain `draw_rectangle()` (no sprite/texture sampled), so unlike `shFlagWave.fsh`/`shPaletteSwap.fsh` it needs NO atlas-UV sub-rect correction -- `v_texcoord` is already a clean 0..1 range across the whole primitive.

**Stage 2 -- trees (`DrawTrees()`, `_TreesProgress()`), concurrent with Stage 1.** `sFateEngineTrees` (a single 2-frame sprite, previously completely unused/unwired in the project) fades in AND parallaxes in from the left, reaching its final state at `FATE_ENGINE_INTRO_TREES_STEPS` = `FATE_ENGINE_INTRO_GRADIENT_STEPS / 2` (now 45 steps, since the derived macro auto-follows Stage 1's x1.5 slowdown) -- literally HALF the gradient's own duration ("twice as fast" per request, not a separately-tuned value). Both frames share the same final centered X (`(guiWidth - spriteWidth) / 2` -- the sprite, at 2884px wide, is wider than the GUI, so this deliberately overflows both edges symmetrically once centered) and the same bottom-anchored Y (`bodyBottomY - spriteHeight`, flush with the play area's own bottom edge -- the sprite's 811px height is almost an exact match for the play area's ~812px height at the current UI bar scale, strongly suggesting the art was authored for exactly this fit). **Index 0 (far layer) draws first/underneath; index 1 (near layer) draws second/on top**, per request. Parallax depth comes from each layer traveling a DIFFERENT distance over the SAME shared (now eased) progress ratio, not different speeds or scales: the near layer travels further (`FATE_ENGINE_TREES_NEAR_PARALLAX_DISTANCE` = 350px) than the far layer (`FATE_ENGINE_TREES_FAR_PARALLAX_DISTANCE` = 150px, both untuned judgment calls) -- the standard "closer things sweep across more for the same motion" parallax depth cue, achieved purely through travel distance since neither layer is scaled differently (would contradict "do not scale up the trees"). **The position lerp's `_t` is run through `_FateEngineEaseInCubic()` first (2026-08-14 follow-up); the alpha fade is NOT** -- see the section intro above. **Drawn at native (1,1) scale** -- per request ("they match the UI scale already"), unlike every other Fate Engine sprite in this file (body, drum items), which are drawn at `FATE_ENGINE_MACHINE_UI_BAR_SCALE`.

**Stage 3 -- machine pop-up (`_MachineProgress()`), begins partway through Stage 2 (OPEN sequence only -- see Close/leave animation below for the unstaggered close timing).** Once `introElapsedSteps` reaches `FATE_ENGINE_INTRO_POPUP_TRIGGER_FRACTION` (0.9) of `FATE_ENGINE_INTRO_TREES_STEPS` -- i.e. once the trees are 90% of the way through their own fade/parallax, per request -- the machine (drum-slot backgrounds, drums, `sFateEngineBody`, the hover tooltip) begins sliding up from fully off-screen below the GUI to its already-established resting position, over its own `FATE_ENGINE_INTRO_POPUP_STEPS` (45 steps, ~0.75s, untuned judgment call; **2026-08-14 follow-up: was 30 steps, raised x1.5**). **Implemented as a `matrix_world` translate wrapping that whole draw group** (`matrix_get`/`matrix_set`/`matrix_build`, restored to the prior matrix immediately after) rather than mutating any drum's own `x`/`y` -- `FateDrum`'s stored position is what `Update()`'s spin/landing math and `GetLockedItem()` (used by `Cashout()`'s reward banking) actually reason about, and none of that needed to change; the pop-up is a purely VISUAL offset applied only at draw time. `_popupOffsetY = lerp(guiHeight, 0, _FateEngineEaseInCubic(machineProgress))` (eased, 2026-08-14 follow-up -- was a raw `lerp(guiHeight, 0, machineProgress)` in the initial pass) -- starting a full GUI-height below (guaranteed off-screen regardless of the machine's actual height) and easing to 0.

**Buttons are deliberately excluded from the pop-up matrix and gated separately.** `FateEngineButtonRects()` anchors near the TOP of the screen (`FATE_ENGINE_BUTTON_TOP_Y = 30`), not physically adjacent to the bottom-anchored machine graphic -- sliding them up from off-screen alongside the machine would look visually disconnected from where they actually live. Instead, both `DrawButtons()`'s call in `Draw()` AND `Update()`'s click-hit-testing block are gated behind `!closing && _MachineProgress() >= 1` (fully popped up, AND not in the middle of the close animation -- 2026-08-14 follow-up, see Close/leave animation below) -- they simply switch on together once the intro finishes, so there's no window where a button is visibly drawn somewhere the click-rect doesn't (yet) match, or vice versa. The hover-tooltip loop (inside the matrix-translated group) is gated the same way, for the same "avoid any drawn-vs-hit-tested position mismatch during the brief animation" reason -- by the time it's allowed to run, `_popupOffsetY` is already exactly 0, so its mouse-position comparison against the drums' own (unshifted) `x`/`y` is correct.

## Close/leave animation (2026-08-14 follow-up request)

`Leave()` no longer closes the overlay instantly -- it now just starts a close animation ("have the fate engine leave the screen in reverse mannor"). No-ops if not open, a session is active, or already closing (unchanged eligibility rules; only the effect changed). It sets `closing = true` and resets `closeElapsedSteps = 0`; the actual state teardown (`isOpen = false`, `global.matchSpeed`/`global.fateEngineOverlayActive` restored) is deferred to `Update()`'s finalization check once the close animation fully finishes. **`isOpen` stays `true` for the ENTIRE close duration** -- this adopts the same idiom `DialogueOverlayScripts.gml`/`PlotHoverScripts.gml` already use for their own fade-outs (a separate `closing` flag drives the outro sub-state while `isOpen` itself doesn't flip until the fade completes), so `oUnitControl/Step_0.gml`'s existing `if (fateEngineOverlay.isOpen) { ...; exit; }` gate keeps suppressing player input and the match stays frozen until the overlay has actually finished visually leaving -- no changes were needed there.

**Reverse playback, not separate close-drawing code.** Rather than writing a second set of draw calls for the outro, the three progress-getter functions themselves became closing-aware and were renamed (`_IntroGradientProgress`/`_IntroTreesProgress`/`_IntroMachineProgress` → `_GradientProgress`/`_TreesProgress`/`_MachineProgress`, since each now serves both directions): when `closing` is true, each returns `1 - clamp(closeElapsedSteps / <itsOwnStepDuration>, 0, 1)` instead of the forward open-ratio. `Draw()`/`DrawTrees()`/`DrawGradientTint()` needed ZERO changes beyond the renamed call sites -- they already just feed whatever the getter returns through the same `lerp()`/`_FateEngineEaseInCubic()` chain, so a reversed ratio naturally plays the exact same eased animation backwards (mathematically, `easeIn(1-t)` sampled forward as `closeElapsedSteps` climbs is the true reverse of `easeIn(t)` sampled forward as `introElapsedSteps` climbed). Net effect: the gradient tint fades back out, the trees fade out AND parallax back out to the left, and the machine pops back down below the GUI -- the exact mirror of the open sequence.

**Unstaggered, unlike the open sequence.** The open intro deliberately staggers its three stages (machine waits until trees hit 90%, per the original request). The close request explicitly asked for the opposite: "have the movement and fade out start immediately, alongside the machine popping down" -- so `_MachineProgress()`'s closing branch has NO trigger-offset; all three stages read off the same `closeElapsedSteps` counter and start together the instant `Leave()` fires. `_CloseTotalSteps()` (new) reflects this -- since nothing is staggered, it's simply `max()` of the three stage durations, not the trigger-offset math `_IntroTotalSteps()` needs for the open sequence.

**Buttons/hover-tooltip during close.** Both were already gated behind `_MachineProgress() >= 1`; that gate got an explicit `!closing &&` added (see Open-intro animation above) for correctness-robustness even though `_MachineProgress() >= 1` during closing is only ever momentarily true right at `closeElapsedSteps = 0`.

**All animation durations 50% slower.** Per "make all of these animations slower by 50%", every STEP-DURATION macro shared by both the open and close sequences was scaled x1.5: `FATE_ENGINE_INTRO_GRADIENT_STEPS` 60→90, `FATE_ENGINE_INTRO_POPUP_STEPS` 30→45 (`FATE_ENGINE_INTRO_TREES_STEPS` is derived as `GRADIENT_STEPS / 2` and follows automatically, 30→45). Deliberately left untouched: `FATE_ENGINE_TREES_*_PARALLAX_DISTANCE` (distances, not durations -- holding them constant while duration increases already slows the apparent motion on its own), `FATE_ENGINE_INTRO_POPUP_TRIGGER_FRACTION` (a relative fraction, not a duration), and `FATE_ENGINE_SPIN_DURATION_STEPS` (the drum-spin gameplay timer -- "these animations" was read as the screen entrance/exit sequence, not gameplay pacing).

## Spin lever (2026-08-14 request)

**Replaces the Spin button entirely** -- `FateEngineButtonRects()` now returns only `{ leave, cashout }`, and `DrawButtons()`/`Update()`'s button-click block dropped every Spin-related check. Spinning is now done by grabbing and pulling `sFateEngineHandle`, a new 3-frame sprite: frame 0 a static base plate (draws, does nothing interactive), frame 1 the animated lever bar, frame 2 the grabbable handle/ball. All three frames share one base anchor (`_LeverHandleBasePosition()`) and are drawn together by `DrawLever()`, called from `Draw()` right after `sFateEngineBody` -- **inside** the same `matrix_world` pop-up/pop-down group as the drums and body, so the lever is "attached to the fate engine" (per request) and slides with the machine during the open/close animation, same as everything else in that group. Unlike the buttons, `DrawLever()` is NOT gated behind `_MachineProgress() >= 1` -- it draws for the whole open/close pop, matching the drums/body it's attached to.

**Positioning (`_LeverHandleBasePosition()`).** Anchor = `sFateEngineBody`'s own draw anchor (`centerX`, `bodyBottomY`) offset by `FATE_ENGINE_HANDLE_ALIGN_X`/`_Y` (92, -101), per request ("align this relative to the fate engine sprite by {+92,-101}"). **Judgment call, flag if wrong:** these offsets (and `FATE_ENGINE_HANDLE_BALL_MAX_DROP_PX`, 17, below) are treated as NATIVE-sprite-space pixels -- i.e. the same coordinate space the art was authored in -- and are scaled by `FATE_ENGINE_MACHINE_UI_BAR_SCALE` (2x) at draw time, exactly like the body sprite's own 240x270-native -> 480x540-on-screen scaling. This was chosen over treating them as literal final on-screen GUI pixels because the request phrases them as offsets "relative to the fate engine sprite," which reads like an art-tool pixel offset against the existing asset, not a screen-space UI coordinate. **If the lever lands roughly 2x further from the body than expected, this is the assumption to revisit** -- swap to un-scaled literal GUI px instead. `FATE_ENGINE_LEVER_PULL_DISTANCE_PX` (110, the drag-distance threshold) is explicitly NOT scaled this way, since it's compared directly against `device_mouse_y_to_gui()` deltas (inherently screen-space).

**Lever bar animation (`_LeverYScale()`, frame 1).** Idles at yscale multiplier `FATE_ENGINE_LEVER_IDLE_YSCALE` (1) and lerps to `FATE_ENGINE_LEVER_PULLED_YSCALE` (-0.25) at full pull, per request. This is a MULTIPLIER on top of `FATE_ENGINE_MACHINE_UI_BAR_SCALE`, not a replacement of it (`draw_sprite_ext`'s yscale param is `FATE_ENGINE_MACHINE_UI_BAR_SCALE * _LeverYScale()`) -- treating the request's "yscale 1"/"yscale -0.25" as absolute engine-level yscale values would draw the lever at a different apparent size than the rest of the (2x-scaled) machine at idle, which didn't seem intended.

**Handle/ball animation (`_LeverHandleBallOffsetY()`, frame 2).** Per the original request: "aligned relative to the handle sprite at {0,0}" (frame 2 shares frame 1's base anchor, no separate static offset). The request's own "the ball is positioned 68px above origin (in the actual frame drawing, no adjustment needed at idle position)" is purely descriptive of the ART -- it explains where the ball visually sits within the frame's own pixel content, but explicitly requires NO code-side offset at idle (offset 0), so 68 never appears in any calculation.

**2026-08-15 follow-up, replaces the original piecewise reading entirely: now a straight LINEAR map directly off `leverProgress`** (0px at `leverProgress` 0, `FATE_ENGINE_HANDLE_BALL_MAX_DROP_PX` at `leverProgress` 1) -- per explicit request, "from the 0 position to 110px mouse movement, the 2nd index of the lever needs to move from 0 to 85px". `FATE_ENGINE_HANDLE_BALL_MAX_DROP_PX` raised 17 -> 85 to match. **This fixes a real bug, not just a tuning tweak:** the original implementation tied the ball's offset to the LEVER BAR's own yscale (not `leverProgress` directly) and only started moving once that yscale crossed 0 into negative -- since `leverProgress` 0->1 maps yscale 1->-0.25 (a span of 1.25), yscale didn't cross zero until `leverProgress` ~0.8, so the ball's offset stayed flat at 0 for the first ~80% of the pull and only ever moved (a mere 17px) over the last ~20% -- reported as "shifts only a little bit when pulling down." The new implementation reads `leverProgress` directly, moving the full distance smoothly across the WHOLE pull.

**Grab detection (`_LeverHandleGrabRect()`).** Per request ("grab...at the top portion of the handles bounding box"): computed from `sFateEngineHandle`'s own configured bbox/origin (via `sprite_get_bbox_*`/`sprite_get_xoffset`/`sprite_get_yoffset`, not hardcoded numbers) at the handle's IDLE position, then the rect is trimmed to its top HALF. **"Top half" is a judgment call** -- the request said "top portion" without an exact fraction; flag if a smaller/larger fraction reads better for grabbing.

**Grab-and-drag state machine (`Update()`, `leverState`: `"idle"` -> `"dragging"` -> `"holding"` -> `"returning"` -> `"idle"`).**
- `"idle"`: watches for `mouse_check_button_pressed(mb_left)` inside the grab rect, but ONLY when `_leverGrabbable` is true -- `!closing && _MachineProgress() >= 1` (fully popped up, matching the buttons' own gate) AND `!_MachineIsSpinning()` AND `_SpinEligible()`. **Per request, "grabbing the lever is only possible when the machine is not spinning, or when the player is allowed to spin"** -- read literally that's an OR, but implemented as AND (both conditions must hold), since OR would allow grabbing while mid-spin whenever the player also happens to be spin-eligible, which doesn't make sense as a mechanic. Flagged judgment call -- revisit if the literal OR was actually intended. **2026-08-16 follow-up (round 2): `_SpinEligible()` was `isSessionActive || hasFateTokens`; now just `isSessionActive`** -- see "Session start moved to Activate()" below. Concretely, the lever can no longer be grabbed at all until a token has been dragged onto the machine first, even if the player is holding Fate Tokens.
- `"dragging"`: `leverProgress` tracks the mouse 1:1 (`clamp(mouseYDelta, 0, 110) / 110`) -- no easing, since this leg is player-driven by hand position, not an animated curve. Reaching `leverProgress >= 1` (110px+ of downward travel, per request) calls `Spin()` and moves to `"holding"`. **2026-08-16 follow-up (round 2): `Spin()` no longer spends a token or starts a session on this call** -- see "Session start moved to Activate()" below; by the time the lever is even grabbable, a session is already guaranteed active.
- `"holding"`: fixed at `leverProgress = 1` for `FATE_ENGINE_LEVER_HOLD_STEPS` (30 steps, ~0.5s, per request "hold at its lowest position for half a second") regardless of further mouse state.
- `"returning"`: eases (`_FateEngineEaseOutCubic`, new helper mirroring `_FateEngineEaseInCubic`'s shape but decelerating INTO rest, matching `TutorialGuideScripts.gml`'s own ease-out convention for things settling into place) from `leverReturnStartProgress` back down to 0 over `FATE_ENGINE_LEVER_RETURN_STEPS` (30 steps, untuned judgment call -- request didn't specify a return duration, only "easing back"), then flips to `"idle"`.
- **Early release (mouse let go before 110px reached) is NOT explicitly covered by the request**, which only describes the full-pull case. Implemented as: ease back to idle from wherever `leverProgress` was (`leverReturnStartProgress = leverProgress` at release), without calling `Spin()`. This is why `"returning"` eases from a variable start point rather than always from 1 -- flag if early release should instead snap back instantly, or behave some other way.

## The Dealer (2026-08-14 request)

`sDealer` -- an 8-frame character sprite (2026-08-14 follow-up: the resource was updated to 8 frames, 284x474, origin now correctly `(0, 474)` bottom-left with no dropdown/sequence mismatch, after the original single-frame integration below was written) -- is drawn leaning against the machine, via `DrawDealer()`, called from `Draw()` right after `DrawLever()`, inside the same `matrix_world` pop-up/pop-down group as the drums/body/lever (so she stays visually attached to the machine during the open/close animation -- **not explicitly requested this time, unlike the lever's stated "attached...for purposes of animation," but assumed for consistency since she's positioned as leaning ON the machine and would look disconnected floating separately mid-animation -- flag if she should instead be excluded from the slide, like the buttons are**).

**Positioning is a "corner alignment," not a simple offset.** Per request: both she and the machine have a conceptual "corner" -- the point of contact where she's leaning -- defined as a fixed pixel offset from each one's OWN sprite origin. Hers: `FATE_ENGINE_DEALER_LEAN_CORNER_X/Y` (`+298, -325`), unscaled since she's drawn native (per request, "will not be scaled up, but keep its scale"). The machine's: `FATE_ENGINE_BODY_LEAN_CORNER_X/Y` (`-28, -108`), scaled by `FATE_ENGINE_MACHINE_UI_BAR_SCALE` at draw time -- **same native-sprite-space assumption already flagged for `FATE_ENGINE_HANDLE_ALIGN_X/Y` (see Spin lever above); if the lever's alignment turns out to need the alternate (literal GUI-pixel) reading, this offset almost certainly needs the same fix.** `_DealerBasePosition()` solves for wherever her own origin needs to land on screen so the two corner points exactly coincide: `dealerOrigin = machineCorner - dealerCorner`.

**Draw order/layering:** drawn after `sFateEngineBody` and `DrawLever()`, so she renders on top of both -- appropriate for "leaning on" imagery (she'd occlude the edge she's resting against, not be occluded by it). The lever sits at `+92` (right of center) and her corner at `-28` (near-center, slightly left), so the two don't overlap and their relative draw order shouldn't matter visually either way.

**Origin data quirk, as originally flagged, is RESOLVED as of the 2026-08-14 follow-up:** the sprite resource was updated (1 frame -> 8 frames) alongside the blink animation work below, and its origin now correctly reads Bottom Left (`origin: 6`, sequence `(0, 474)`, matching a 284-wide sprite) with no dropdown/sequence mismatch -- the earlier "worth a look in the sprite editor" note no longer applies to the current resource. `_DealerBasePosition()`'s corner-alignment math is unaffected either way, since it only ever reads the sequence-level `xorigin`/`yorigin` implicitly through wherever `draw_sprite_ext` actually anchors the sprite -- it never hardcoded the old (400, 450) dimensions.

### Blink animation (2026-08-14 follow-up request)

"Add a somewhat random but rhythmic timing for when she blinks (not constantly, but every few seconds with some slight variation). This animation lives in her existing sprite, with index 0 being idle, and the rest played out from start to finish, looping back to 0." `DrawDealer()` no longer hardcodes frame 0 -- it now draws whatever `dealerBlinkFrame` currently is, driven by a small state machine ticked once per `Update()` call (unconditionally, alongside the drums -- runs even mid open/close pop, which is harmless since she isn't visible off-screen anyway, and keeps her rhythm continuous rather than pausing/resuming oddly around the overlay's own animation).

**State machine (`dealerBlinkState`: `"idle"` <-> `"blinking"`, `dealerBlinkFrame`: 0 or 1-7, `dealerBlinkTimer`: a shared countdown reused by both states).**
- `"idle"`: counts `dealerBlinkTimer` down; at 0, moves to `"blinking"`, sets `dealerBlinkFrame = 1`, and starts a fresh per-frame hold via `_DealerBlinkFrameSteps()`.
- `"blinking"`: holds the current frame for `_DealerBlinkFrameSteps()` steps, then either advances to the next frame (re-arming the same per-frame hold) or, once `dealerBlinkFrame` reaches 7, loops back to `"idle"` with `dealerBlinkFrame = 0` and a freshly rolled `_DealerNextBlinkIntervalSteps()` wait.

**Timing between blinks (`_DealerNextBlinkIntervalSteps()`).** Uniform random between `FATE_ENGINE_DEALER_BLINK_INTERVAL_MIN_STEPS` (180, 3s) and `_MAX_STEPS` (300, 5s), re-rolled after every blink -- per request "somewhat random but rhythmic... every few seconds with some slight variation." **Untuned judgment call on the exact 3-5s range and on "uniform random" as the specific distribution** -- the request specified the FEEL, not exact numbers or a distribution shape. Flag if blinks should feel more clustered around a central value (e.g. a narrower/bell-shaped range) rather than uniformly spread across the whole 3-5s window.

**Timing WITHIN a blink (`_DealerBlinkFrameSteps()`).** Rather than picking a new arbitrary per-frame duration, this defers to `sDealer`'s own baked `playbackSpeed` (10 FPS, as authored in the sprite editor) -- "this animation lives in her existing sprite" was read as "respect the sprite's own authored pacing," not just "reuse its frame art at some new arbitrary speed." Converts FPS to steps via `room_speed` (`sprite_get_speed`/`sprite_get_speed_type` queried live, not cached, so it stays correct if the sprite's authored speed is ever retuned in the editor) -- at the current 10 FPS and 60 steps/sec room speed, that's 6 steps (0.1s) per frame, so the full 7-frame blink (indices 1-7) takes roughly 0.7s. **Flag if that reads as too slow/deliberate for a blink** (real blinks are often faster, ~0.1-0.4s total) -- the sprite's own baked speed was trusted over guessing a different one, but if the art wasn't actually authored with THIS use in mind, a dedicated (faster) macro might read better.

**Reset on `Open()`:** `dealerBlinkState`/`dealerBlinkFrame`/`dealerBlinkTimer` are reset to a clean idle face with a freshly rolled wait every time the overlay opens, rather than resuming wherever a previous session's close animation happened to cut her off (which could otherwise leave her frozen mid-blink for a moment on next open) -- same "replay fresh" precedent `introElapsedSteps` already established.

## Machine hold/release + interaction lock (2026-08-14 follow-up, "Dealer intro" tutorial-continuation scene)

Added to support `DealerIntroScripts.gml`'s scripted ambush scene, which needs to open this overlay with the gradient/trees background animating in while the drums/body/lever/Dealer group stays fully withheld off-screen, then release that group later on its own cue, and separately keep the buttons/lever non-interactive for a stretch even after the machine is fully popped up. Every new field defaults to/resets to the "normal" (unheld, unlocked) value on every `Open()` call unless the new optional `_holdMachine` param is passed `true` -- so every OTHER caller (the XP-bar click, in particular) is completely unaffected; this is purely additive.

**`Open(..., _holdMachine = false)`.** New trailing optional param. `false` (every existing call site): behaves exactly as before. `true`: `machineHeld`/`machineHoldUsed` both set true, `interactionLocked` set true -- the gradient tint and trees still animate in on the normal `introElapsedSteps` schedule, but `_MachineProgress()` is forced to 0 for as long as `machineHeld` stays true (see below), and the buttons/lever/hover-tooltip are suppressed regardless of pop-up state.

**`ReleaseMachine()`** (new). Clears `machineHeld` and resets `machineReleaseElapsedSteps` to 0 -- from this exact moment, `_MachineProgress()` switches to counting `machineReleaseElapsedSteps` (a NEW, independent counter, ticked in `Update()` only while `machineHoldUsed && !machineHeld`) up to `FATE_ENGINE_INTRO_POPUP_STEPS`, completely independent of `introElapsedSteps` (which may already be long finished by the time a scripted scene actually calls this). No-ops harmlessly if the overlay wasn't opened with `_holdMachine` true. Does NOT clear `interactionLocked` -- a scene may want the machine visually popped up for a while before the player can actually touch it (exactly the Dealer scene's own "TA-DA! ... pull the lever" beat, where several more lines play after the machine is fully visible).

**`UnlockInteraction()`** (new). Clears `interactionLocked` only. Independent of `ReleaseMachine()` by design -- see above.

**`LockInteraction()`** (2026-08-15 follow-up, new). The exact inverse -- sets `interactionLocked = true` on an already-open overlay. Added for `DealerIntroScripts.gml`'s post-first-spin follow-up monologue: that scene needs to pause an already-open, already-popped-up (never re-`Open()`'d) machine for a SECOND scripted beat after briefly handing the player real control, and `Open(..., true)` isn't reusable mid-session for this (it resets far more state than just the lock). See `DealerIntroScripts.md`'s "2026-08-15 (round 2)" section.

**`_IntroTotalSteps()`/`_MachineProgress()` branching.** Both check `machineHoldUsed` first: if true, `_IntroTotalSteps()` no longer includes the popup-trigger-fraction math at all (the machine's completion is on its own separate track, driven by `machineReleaseElapsedSteps`, not `introElapsedSteps`), and `_MachineProgress()` returns 0 flat while `machineHeld`, else `clamp(machineReleaseElapsedSteps / FATE_ENGINE_INTRO_POPUP_STEPS, 0, 1)`. If `machineHoldUsed` is false (every normal caller), both functions fall through to their original formulas, byte-for-byte unchanged.

**Interaction gating.** `interactionLocked` was added as a THIRD condition (alongside the existing `!closing` and `_MachineProgress() >= 1`) on: the button-click handling block, the lever-grabbable check (`_leverGrabbable`), the hover-tooltip loop, and `DrawButtons()`'s own call in `Draw()`. This is deliberately a SEPARATE gate from `_MachineProgress() >= 1` (not folded into it) -- the machine can be fully visible (`_MachineProgress() == 1`) while a scripted scene is still narrating over it, same as the Dealer's own "TA-DA! ... Introducing The Fate Engine! ... Just insert the token and pull the lever..." run of lines, several of which play AFTER the machine has finished popping up but BEFORE the player should be able to touch it.

**One-directional coupling, by design.** This file has zero references to `DealerIntroScripts.gml`/`DealerIntroScene` or any Dealer-scene-specific concept -- `DealerIntroScripts.gml` calls INTO these new methods and reads the existing `_GradientProgress()`/`_MachineProgress()`/`_DealerBasePosition()`, never the reverse. Keeps this file's own responsibility (the Fate Engine session itself) decoupled from any one caller's scripted-scene needs.

**Known gotcha for any `_holdMachine = true` caller (2026-08-15, caught in `DealerIntroScripts.gml`'s own use): `Open()`'s `savedMatchSpeed = global.matchSpeed;` capture is only correct if `global.matchSpeed` genuinely holds the pre-session speed at the moment `Open()` is called.** If the CALLER has already zeroed `global.matchSpeed` itself before calling `Open(..., true)` (exactly what `DealerIntroScripts.gml`'s own scene-wide freeze does), `savedMatchSpeed` captures 0 instead of the real speed -- and since a held-open session can stay open indefinitely (through to the player's own later Leave()), that stale 0 eventually gets written back to `global.matchSpeed` on close, freezing the match permanently. This file's own `Open()`/`Leave()`/`Update()` were deliberately NOT changed to work around this (would require this file to know about caller-side freezes it has no business knowing about) -- instead, any caller that freezes the match itself BEFORE a held `Open()` is responsible for resyncing `<overlay>.savedMatchSpeed` to the correct value once it releases its OWN freeze (see `DealerIntroScripts.gml`'s `_ConcludeScene()`, which does exactly this). Flag this doc note to any FUTURE `_holdMachine` caller.

## Machine activation + dim/lit drums + particle burst (2026-08-16 follow-up request)

**"Update the fate token functionality. When you click and hold from this portion of the UI (while the fate engine is open), have the large fate token draw at the mouse position, and one of the tokens be removed. If you drag this token up to the center of the screen (roughly where the machine is), spend the token to 'activate the machine'... by having the token disappear and a number of purple and gold particles rise up from where the token disappeared to. When the machine is not active, have the drums be dimmed out, with no symbols on them. When the machine activates, have the dimming fade away, as well as the symbols fade in. When the machine is cashed out, have it INSTANTLY return to the dimmed state."**

**Split of responsibility between this file and `XpBarScripts.gml`.** The drag pickup/hold/drop interaction itself (clicking a region token, tracking the mouse, deciding whether a release landed "roughly where the machine is") lives entirely in `XpBarScripts.gml`'s `StepTokenDrag()`, since that's where the token visually comes from (the region-token pile below the XP bar, see the "Region tokens" section of `XpBarScripts.md`) and where the large-token drag sprite is drawn. This file only exposes the pieces `StepTokenDrag()` needs to make its own drop-eligibility decision (`_TokenActivateEligible()`, `_DistanceToMachineCenter()`) and the actual state-changing call once it decides to activate (`Activate()`). **`Activate()` itself does NOT touch `global.resources[...].fateTokens`** -- the caller spends the token (and re-syncs its own `lastFateTokens`) BEFORE calling `Activate()`, so this file never needs to know anything about where its tokens come from. Same one-directional-coupling convention already established for `DealerIntroScripts.gml` above -- `XpBarScripts.gml` reaches INTO this file's methods, never the reverse.

**`machineActive` and `isSessionActive` were originally independent; RESOLVED as of the 2026-08-16 follow-up (round 2), see "Session start moved to Activate()" below.** They're not the same flag (`machineActive` still drives visuals, `isSessionActive` still gates Leave/Cashout/the lever), but as of round 2 they can no longer drift apart -- `Activate()` is now the only place that sets `isSessionActive = true`, and it always does so in the same call that sets `machineActive = true`. The original "spin via the old lever flow without ever activating leaves the drums dimmed" gap is no longer reachable, since `Spin()` now requires `isSessionActive` (see `_SpinEligible()`), which can no longer become true without `machineActive` also becoming true in the same call.

**Double-spend risk between the two token-spend paths -- RESOLVED as of the 2026-08-16 follow-up (round 2).** The original design had `Spin()` spend its own token to start a session, entirely separate from `Activate()`'s (then-nonexistent) spend. As of round 2, `Spin()` no longer spends a token or starts a session at all -- see "Session start moved to Activate()" below. There is now exactly ONE code path that starts a session and spends a token: dragging a token onto the machine.

**`Activate()` is idempotent** (no-ops if `machineActive` is already true) -- guards against a caller somehow calling it twice (e.g. two drops in quick succession) restarting the fade or double-spawning a burst.

**Fade is asymmetric by explicit request: smooth up, instant down.** `machineActiveFade` eases 0->1 over `FATE_ENGINE_ACTIVATE_FADE_STEPS` (45 steps, ~0.75s, untuned judgment call -- matches `FATE_ENGINE_INTRO_POPUP_STEPS`'s own duration since both are "something on the machine finishing a pop/reveal," no other guidance given) while `machineActive`, ticked in `Update()` independent of `global.matchSpeed` (matchSpeed is 0 the whole time the overlay is open, same convention every other animation in this file already follows). `Cashout()` snaps both `machineActive` and `machineActiveFade` straight to `false`/`0` with no easing at all, per request's own explicit framing ("INSTANTLY... this simulates the lights turning on, then cutting out"). `Open()` also defensively resets both to the same off state -- not explicitly named by the request (which only calls out Cashout as a reset trigger), but a fresh session starting mid-lit would look wrong; judgment call, flag if a held-open session should instead preserve activation state across an intervening close/reopen (currently it can't, since `machineHeld`/normal `Open()` calls both reset unconditionally).

**Dim rendering (`Draw()`).** The drum slot-rectangle fill color blends between `FATE_ENGINE_DRUM_DIMMED_COLOR` (a dark, desaturated version of the existing lit fill, `make_color_rgb(0x40,0x38,0x48)`, judgment call) and the rectangle's own pre-existing lit color (`0xE1D3EA`) via `merge_color(..., ..., machineActiveFade)`. The drum items/symbols themselves ("no symbols on them" while dimmed) are handled by wrapping the whole `drums[i].Draw()` loop in `draw_set_alpha(machineActiveFade)` rather than touching `FateEngineDrumScripts.gml` at all -- `FateDrum.Draw()` has no alpha parameter of its own, but `draw_sprite_ext()`'s externally-set `draw_set_alpha()` multiplies with whatever alpha `FateDrum.Draw()` draws at internally, so this achieves the fade with zero changes to that file. At `machineActiveFade == 0` the item sprites are fully invisible ("no symbols"); the slot rectangle itself stays visible throughout (just recolored), since the request only asked for the drums to read as "dimmed out," not disappear entirely.

**Particle burst (`_SpawnActivateParticles()`, stepped in `Update()`, drawn in `Draw()`).** A plain GUI-space struct-array system -- `activateParticles`, each `{ x, y, vx, vy, color, size, life, lifeMax }` -- deliberately following `XpBarWidget`'s own tossed-coin precedent (`tokens`, see `XpBarScripts.md`) rather than `ResourceParticleScripts.gml`/`oResourceProducedParticle`, which is room-space (`instance_create_layer` at building x/y) and would render in the wrong place entirely for this GUI-space HUD event. `FATE_ENGINE_ACTIVATE_PARTICLE_COUNT` (16, untuned) particles spawn per burst, half purple (`FATE_ENGINE_ACTIVATE_PARTICLE_PURPLE_COLOR`, matches `DEALER_INTRO_TEXT_COLOR`'s own purple) half gold (`_GOLD_COLOR`, matches `TUTORIAL_GUIDE_HIGHLIGHT_COLOR`'s own gold-orange) on average -- both reused from existing macros elsewhere in the project rather than inventing new colors, per the "duplicate judgment-call macros per-system, reuse pure-geometry/pre-registered-tag constants across systems" convention. Each gets a random outward burst velocity (`FATE_ENGINE_ACTIVATE_PARTICLE_SPEED_MIN/MAX`) PLUS a constant `FATE_ENGINE_ACTIVATE_PARTICLE_RISE_BIAS` upward drift baked directly into `vy` at spawn -- per request, "particles rise up," not a purely omnidirectional puff. Each fades out linearly over its own `life`/`lifeMax` (`FATE_ENGINE_ACTIVATE_PARTICLE_LIFE`, 50 steps) and is `array_delete`d on expiry, both independent of `global.matchSpeed` like everything else in this file. Rendered as small filled squares (`draw_rectangle`, `FATE_ENGINE_ACTIVATE_PARTICLE_SIZE_MIN/MAX` half-extent) rather than a sprite -- no dedicated particle sprite asset exists for this, and a plain colored square was judged sufficient for a brief rising burst; flag if a softer/rounder particle sprite should be authored instead.

### Session start moved to `Activate()` (2026-08-16 follow-up, round 2)

**"Remove spin on session start logic, spending the token starts the session, not resolving until at least one spin has been done."** This is a real gameplay-behavior change, not just a refactor -- previously, pulling the lever with NO active session would itself spend a Fate Token and start one (`Spin()`'s old `if (!isSessionActive) { spend; isSessionActive = true; }` branch); now that branch is gone entirely, and `Spin()` unconditionally requires `isSessionActive` to already be true, or it no-ops.

**`Activate()` is now the sole session-start path.** Dragging a token onto the machine (`XpBarScripts.gml`'s `StepTokenDrag()`, see that file's own section) both spends the token (in the caller, unchanged) and, in the same `Activate()` call, sets `isSessionActive = true` and resets `pendingRewards = []`/`hasSpunThisSession = false` for the fresh session -- this is exactly the reset work `Spin()`'s old session-start branch used to do, just relocated. **Concrete consequence: a player can no longer just walk up and pull the lever to spend a token and start playing.** They must drag a token onto the machine first (which also activates the visual lit/dimmed state) -- ONLY THEN does the lever become grabbable (`_SpinEligible()` is now just `isSessionActive`) and spinnable.

**`_TokenActivateEligible()` now also requires `!isSessionActive`** -- a second token can't be dropped onto an already-active session (nothing left to "activate"), which is also what prevents the token spend from ever happening twice for one session.

**"Not resolving until at least one spin has been done" -- new `hasSpunThisSession` field.** Set `true` in `Update()`'s `resultsBanked` block, the moment a spin's results actually land -- NOT at `Activate()` time. `Cashout()` (and the Cashout button's own enabled state, `DrawButtons()`, and the button-click handler in `Update()`) now all require `isSessionActive && hasSpunThisSession` -- a session that's been started (token spent, machine lit) but never spun shows a greyed-out, non-functional Cashout button, since there's nothing rolled yet to grant. Reset to `false` on `Cashout()` (session ending) and defensively on every `Open()` (fresh session), matching `machineActive`'s own reset pattern.

**Leave() is unaffected.** It was already, and remains, gated purely on `!isSessionActive` -- a player who's activated the machine but hasn't spun yet still can't Leave (must resolve the session first, one way or another), same as before. This doc doesn't add a "Leave while activated-but-unspun" escape hatch; flag if one should exist (e.g. an "undo activation" path that refunds the token) -- not requested, not built.

## Corruption (2026-08-16 follow-up request)

**"To show corruption, I have added lights to be placed at the following coordinates... The four positions given are the 'charge up in corruption'. Have them fade in when gained. When a full level of corruption is gained... have each instantly shut off in succession (4 to 1) before allowing spins again."** 5 levels (0-4), one per face color (White/Blue/Green/Yellow/Purple), each gated behind a 4-light charge bar that fills via re-spins.

**Two genuinely blocking ambiguities were resolved via `AskUserQuestion` before implementing, not guessed:**
1. **Charge trigger.** Nothing in the request named what causes a charge light to be gained. User confirmed: **each `Spin()` call AFTER the session's first** ("each Spin() after the initial one... I feel like we had this in here already") -- this reuses `hasSpunThisSession` (added in the session/spin-decoupling pass just before this one) as the exact signal: `Spin()` only calls `_GainCorruptionCharge()` when `hasSpunThisSession` is already `true` at call time, which is precisely "not this session's first spin." Resets naturally every session (since `Activate()` resets `hasSpunThisSession` to `false`), so corruption charge only progresses on re-spins, session after session.
2. **Level 1's color.** The request named `sFateEngineFaceWhiteStart/Loop/End` three times in a row for "reaching corruption level 1" -- but the given order (White, Blue, Green, Yellow, Purple) lines up 1:1 with levels 0-4, which exactly matches the charge-light pairing given for levels 3/4 (Yellow flame, Purple flame). User confirmed this was a typo: **each level uses its own color** -- level 0 = White (baseline only, never animated), level 1 = Blue, level 2 = Green, level 3 = Yellow, level 4 = Purple. `global.fateEngineCorruptionFaceStart/Loop/End[corruptionLevel]` implement this directly.

**Persists across `Open()`/`Close()` -- NOT reset per session.** `corruptionLevel`/`corruptionCharge`/`corruptionChargeLightAlpha` are the MACHINE's own permanent state (unlike `machineActive`/`hasSpunThisSession`, which are per-session and reset every `Open()`). Judgment call, not explicitly specified -- flag if corruption should instead reset when the overlay closes or a session ends.

**Charge lights -- 4 mirrored pairs, positioned in native-sprite-space px relative to `sFateEngineBody`'s own TOP-LEFT corner** (`_originX`/`_originY` in `DrawCorruption()`, derived via `sprite_get_xoffset`/`sprite_get_yoffset(sFateEngineBody)` -- same "read the sprite's own configured origin, don't hardcode it" convention `XpBarWidgetHitRect()` already uses for `sXpBar`), scaled by `FATE_ENGINE_MACHINE_UI_BAR_SCALE` at draw time -- the same native-sprite-space family as `FATE_ENGINE_HANDLE_ALIGN_X/Y`/`FATE_ENGINE_BODY_LEAN_CORNER_X/Y` above, this time relative to a DIFFERENT anchor (top-left corner, not `centerX`/`bodyBottomY`) per how the request phrased it ("relative to the fate engine top left corner"). The 8 literal coordinates given are used as-is (`global.fateEngineCorruptionLightOffsets`), not derived via a left/right mirror formula -- the pairs aren't perfectly symmetric about the body's centerline (e.g. pair 1 is 39/200, a mirror formula off `width - x` would give 201, not 200), so using the exact given numbers avoids introducing an assumption the art may not actually follow.

**Charge-light sprite/frame depends on `corruptionLevel` (the level being charged TOWARD, i.e. the current level), not per-light-position:** levels 0-2 pick a STATIC frame of `sFateEngineLights` (which has exactly 3 frames, one per level, confirmed via the sprite asset); levels 3-4 switch to fully different, fully ANIMATED sprites (`sFateEngineFlameYellow`/`sFateEngineFlamePurple`). ALL currently-lit lights share the exact same sprite/frame at any given moment (`_CorruptionChargeLightSprite()`), including a single shared animation frame for the flame sprites (`corruptionFlameFrame`) rather than a separately-phased one per light -- simplifying judgment call, flag if the flames should look less uniform/more organic (phase-offset per light).

**Fade-in on gain, per request ("have them fade in when gained").** `corruptionChargeLightAlpha[i]` (NOT `corruptionCharge` itself) is what `DrawCorruption()` actually reads -- `_GainCorruptionCharge()` resets a light's alpha to 0 and `_StepCorruptionChargeLights()` eases it back to 1 over `FATE_ENGINE_CORRUPTION_LIGHT_FADE_STEPS` (20 steps, ~0.33s, untuned judgment call -- no duration was specified). Deliberately decoupled from the numeric `corruptionCharge` counter (which resets to 0 the instant a level-up begins) specifically so a light can stay visually lit at full alpha through the ENTIRE level-up face animation, only actually switching off later once the shutoff sequence explicitly zeroes it -- see below.

**Level-up sequence, once the 4th light is gained (`_BeginCorruptionLevelUp()`):** `corruptionLevel` increments immediately, `corruptionCharge` resets to 0 (logically ready for the next level's charge cycle -- the lights themselves stay lit, per above), `corruptionLevelingUp` is set `true` (blocks `_SpinEligible()`/`Spin()` itself, see below), and the face immediately begins playing the NEW level's `Start` sprite. **The 4 lights do NOT switch off at this point** -- they stay lit through the whole `Start` + `Loop` animation.

**Face state machine (`_StepCorruptionFace()`, `corruptionFacePhase`: `"idle"` -> `"start"` -> `"loop"` -> `"idle"`).** "This will be how all faces are handled" -- every level's face (1-4; level 0 never animates, it's the raw starting baseline) plays its OWN color's `Start` sprite through once (frame timing derived from that sprite's own baked `playbackSpeed`, same `_DealerBlinkFrameSteps()`-style convention generalized into `_CorruptionFaceFrameSteps(_sprite)`), then its OWN color's `Loop` sprite, held/cycled for exactly `FATE_ENGINE_CORRUPTION_LOOP_HOLD_STEPS` (60 steps = 1 second, per request), then settles into `"idle"` -- which just means `DrawCorruption()` shows `corruptionLevel`'s own `End` sprite at its LAST frame (`sprite_get_number(...) - 1`), per request ("stopping at its last index for idling until the next corruption level is gained"). Frame counts vary wildly per color/phase (Start: White=2, Blue=3, Green=3, Yellow=13, Purple=6 frames; Loop: White/Blue/Green=1 frame each -- effectively a static held pose for those three -- Yellow/Purple=4 frames, an actual cycling flicker) -- all confirmed via the sprite assets, all respected automatically by reading each sprite's own frame count/speed rather than hardcoding per-color numbers.

**Light shutoff, triggered by Loop finishing (NOT concurrent with the face settling to idle).** The instant the 1-second Loop hold elapses, `corruptionFacePhase` moves to `"idle"` (face now shows the new level's End sprite) AND, in the same step, `corruptionShutoffIndex` is set to 3 -- kicking off a SEPARATE process (`_StepCorruptionChargeLights()`) that, every `FATE_ENGINE_CORRUPTION_SHUTOFF_STEP_STEPS` (10 steps, untuned guess at "in succession" -- no duration given), snaps exactly one light's alpha INSTANTLY to 0 (no fade -- fading is only for gaining a light, not losing one, per request) and moves to the next index down: 3 (pair 4), then 2 (pair 3), then 1 (pair 2), then 0 (pair 1) -- "4 to 1", per request. The moment the LAST light (pair 1, index 0) switches off, `corruptionLevelingUp` clears, per request ("...before allowing spins again").

**`corruptionLevelingUp` blocks spinning at TWO points, defense-in-depth:** `_SpinEligible()` (so the lever can't even be grabbed) and directly inside `Spin()` itself (since `Spin()` remains independently callable, same pattern `isSessionActive`'s own guard already uses in both places).

**Capped at level 4 (Purple) -- no level 5.** `_GainCorruptionCharge()` no-ops once `corruptionLevel >= FATE_ENGINE_CORRUPTION_MAX_LEVEL` -- matches the 5 face color sets that actually exist (no 6th color, no `sFateEngineFlame*` beyond Yellow/Purple). Once maxed, further re-spins simply never grant charge again; the machine stays permanently at Purple.

**Purely cosmetic for now.** Corruption doesn't affect spin odds, rewards, or any other gameplay system in this pass -- `FateEngineDrumScripts.md` already flagged "no corruption-scaling/event-type rewards exist yet" as a known future direction; this pass only builds the visual/state machinery, not any reward-scaling hook. Not requested this turn, not built.

**`sFateEngineFacePurpleEnd`'s origin, corrected 2026-08-16 follow-up.** Originally flagged as `(0,0)` against every sibling face sprite's `(16,28)` when this section was first written; on request ("origin should be corrected") this was re-checked directly against the live asset and found to already read `(16,28)` -- matching its siblings, no asset edit was actually needed at that point. The code-level `+16,+28` compensation `DrawCorruption()` briefly carried for this one sprite has been removed accordingly, since the sprite's own origin now handles it like every other face sprite already did.

**Known minor edge case, not guarded against:** if a session ends (`Cashout()`) while `corruptionLevelingUp` is still true (e.g. the charge-completing spin was also the session's LAST spin before cashing out), the leftover shutoff sequence (well under 1 second total) will still block the very first spin of the player's NEXT session for its remaining duration, even though that's a different session. Not worth extra guarding for a sub-second, rare overlap -- flagged for awareness only.
