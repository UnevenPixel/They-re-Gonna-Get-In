# oUnitControl

The player-side (`TEAM.PLAYER`) gameplay HUD/input controller -- owns every selection/order/blueprint/hover/menu/overlay controller and dispatches input to them in a specific, load-bearing order each Step.

## Create_0

Instantiates every owned controller: `selectionController` (`SelectionController`, drag-select/orders), `orderMenu`, `blueprintController`, `xpBarWidget` (lower HUD, 2026-07-06), `plotHoverController`/`buildingHoverController`/`unitSelectHoverController` (hover data cards, 2026-07-06/08/11), `rulerPortraitController` (animated portrait, 2026-07-11), `castleGarrisonMenu` (castle-wall-click dropdown, 2026-07-11), `selectionSummaryMenu` (top-left multi-select panel, 2026-07-12), `castleBonusHoverController` (stationed-bonus hover panel, 2026-07-12), `armyLimitMenu` ("Unit Limits" dropdown, 2026-07-13), `fateEngineOverlay` (2026-07-13), `settingsOverlay` (2026-07-14, instantiated BEFORE `pauseMenu` since it's passed to that constructor), `pauseMenu` (2026-07-13, takes `settingsOverlay` as its settings sub-menu).

## Step_0

Order matters throughout this event -- see below.

**Dealer-intro scene gate, checked FIRST of all (2026-08-14 follow-up, ahead of even the overlay gate below).** `global.dealerIntro.Update(...)` runs unconditionally every Step (cheap no-op outside the scene); if `IsSuppressingInput()` is true, the four world-hover `.Step()` calls run (2026-08-15 bugfix, see below) and the frame `exit`s. See `DealerIntroScripts.md`.

**Overlay gate, checked next.** `fateEngineOverlay.isOpen` is checked before anything else remaining; while open, its own `Update()` runs, **plus (2026-08-16 follow-up) `xpBarWidget.Step(fateEngineOverlay)`** -- everything else this frame still `exit`s. `pauseMenu.isOpen` is checked second, right after -- same full-suppression pattern. This ordering is what makes the two overlays mutually exclusive: the XP-bar click can't open the Fate Engine overlay while paused, and (since the Fate Engine check already exited if it was open) Escape can't open the pause menu while the Fate Engine overlay is up.

**`xpBarWidget.Step(fateEngineOverlay)` now runs from TWO places (2026-08-16 follow-up).** The overlay-open branch above (so the new click-and-drag Fate Token interaction -- see `XpBarScripts.md`'s "Token drag-to-activate" -- keeps working while the overlay is open, since this gate would otherwise skip the Independent-systems call below entirely) AND its original call in the Independent-systems block further down. Same "caller keeps ticking a system this gate would otherwise skip" pattern `global.dealerIntro.Update()`'s own `fateEngineOverlay.Update()` call already uses, just in the reverse direction (the Dealer scene reaches into the overlay; here the overlay-open gate reaches into the XP bar).

Escape opens the pause menu (`pauseMenu.Open(...)`), checked before targeting/dragging/menu state below since `Open()` already cleanly resets all of that itself.

A press on the XP bar's hit rect (`XpBarWidgetHitRect()`) opens the Fate Engine overlay, checked before targeting/dragging/menu state for the same reason -- `Open()` cancels targeting, cancels a blueprint drag, and closes every dropdown itself.

**Dead-unit prune, before anything reads selection.** `selectionController.PruneDeadSelected()` runs before orderMenu's right-click-to-open path, `IssueOrder`, and `unitSelectHoverController.Step` -- combat's `instance_destroy` has no hook back into selection state, so this fixes a crash flagged in `NIGHTLY_REVIEW_2026-07-09.md` §3.1 (critical).

**Menu `.Update()` calls run BEFORE this frame's open-click handling, always in this order: `orderMenu`, `castleGarrisonMenu`, `armyLimitMenu`, `selectionSummaryMenu.Step`, `blueprintController.UpdatePaging()`.** This ordering exists specifically to avoid a same-frame open/close bug: if a menu were opened via `Open()` first and then `Update()` ran afterward in the same Step, the same right-click that just opened it would still read as pressed inside `Update()` and immediately close it again -- open and close within one frame, never visible. Running `Update()` first means it only ever sees `isOpen` as it was at the START of the frame.

- `castleGarrisonMenu.Update()`: clicking a row deploys one unit of that type (`DeployStationedUnit`) -- undefined return is a safe no-op for a dismiss click or the "--" row.
- `armyLimitMenu.Update()`: clicking a row selects every currently DEPLOYED (live, not stationed) unit of that type (`SelectAllOfType`), then instantly opens the order menu centered on screen (`OpenCentered`, 2026-07-13) since the click came from a HUD dropdown, not a playfield click.
- `selectionSummaryMenu.Step()`: own hover/click handling for the top-left panel (2+ units selected, 2026-07-12); sets `consumedClick` when a row was clicked. Also instantly opens the order menu, centered, if a row click narrowed the selection (2026-07-13).
- `blueprintController.UpdatePaging()`: page-arrow click + scroll-wheel paging (2026-07-13); returns true if an arrow click was consumed, checked below so that same press doesn't also fall through to drag/selection logic.

**Click routing** (targeting > blueprint-drag > everything else): while `selectionController.isTargeting`, drag-box selection and normal left-click are suspended -- `UpdateTargeting()` consumes the click instead. A blueprint drag (`blueprintController.dragging`) suspends the same things and takes priority over starting a new selection box.

Otherwise, a left click is routed by priority, all gated behind `!castleGarrisonMenu.consumedClick && !selectionSummaryMenu.consumedClick && !armyLimitMenu.consumedClick && !_clickedBlueprintArrow` (2026-07-12/13 fix -- without this guard, a click a menu just consumed for deploy/select would ALSO fall through and clobber what the menu just did, e.g. a drag-select clearing a selection a summary-row click just set):

1. Army Limit Widget icon hit rect (GUI-space HUD icon, checked first since it sits below `SELECTION_DRAG_MIN_GUI_Y` and could never start a drag anyway, but could still coincidentally overlap a room-space instance depending on camera position) -> opens the "Unit Limits" dropdown.
2. Castle wall click (`oPlayerCastle` only) -> opens the garrison dropdown, but ONLY if the click ISN'T also on an inside plot -- `oPlotSpawner` spawns inside-castle plots literally within the castle's own footprint, so plots are checked FIRST and take priority (2026-07-11: "the castle wall itself, not the plots in the castle").
3. Friendly training building click -> queues one unit (`TrainingTryQueueUnit`) -- checked before blueprint-drag/selection-drag since "click a building I own" should win over "start dragging a selection box under it".
4. Filled blueprint slot click -> starts a blueprint drag (`blueprintController.TryBeginDrag()`); only if that fails does a unit-selection drag start instead (`selectionController.BeginDrag()`).

On left-release: `selectionController.EndDrag(shift-held)`, then instantly opens the order menu anchored at the release point if the drag/click populated the selection (2026-07-13) -- no-ops via `Open()`'s empty-orders guard on an empty-space click or a selection with no common order.

On right-click with a non-empty selection and no menu already open: opens the order menu anchored at the click point.

**Independent systems**, run every Step regardless of the above: `UpdateCameraPan()`, `xpBarWidget.Step(fateEngineOverlay)` (2026-08-16 follow-up -- now takes the overlay reference, see above), `plotHoverController.Step(...)`/`buildingHoverController.Step(...)`/`castleBonusHoverController.Step(...)` (each suppressed internally while targeting/dragging; the castle-bonus one is additionally forced off while `castleGarrisonMenu.isOpen`), `blueprintController.UpdateHover()`, `unitSelectHoverController.Step(...)` (mutually exclusive with `selectionSummaryMenu` -- exactly-1-selected vs. 2+-selected, same top-left corner), `rulerPortraitController.Step()`.

**Guided tutorial gate (2026-08-13, extended same day), checked after Escape/before the XP-bar click.** `global.tutorialGuide.Update()` runs whenever she's present in any capacity (`state != "hidden"`), independent of the restriction below. While `global.tutorialGuide.restrictionActive`, everything past this point is suppressed via `exit` -- only `blueprintController`'s paging/hover/drag-start/drag-end/cancel run, PLUS (2026-08-13, added for the Peasant Ward guided-tutorial phase) a training-building click routes to `TrainingTryQueueUnit` the same way it does in the unrestricted click-routing block above, checked before falling through to `blueprintController.TryBeginDrag()`. The actual "which building, which plot, how many trained" enforcement lives in `TryPlaceBlueprint`/`TrainingTryQueueUnit`'s callers into `TutorialGuide` (`BlueprintScripts.gml`/`TrainingScripts.gml`), not here. Escape is deliberately checked BEFORE this gate so pausing still works during a restriction. **2026-08-14: this gate now ALSO runs the four world-hover `.Step()` calls (`plotHoverController`/`buildingHoverController`/`castleBonusHoverController`/`unitSelectHoverController`)** -- previously these never ran at all during a restriction (their `.Draw()` calls in `Draw_64` run unconditionally regardless, so hover cards just stayed stale/blank the whole time), per request ("don't block hover displays during the tutorial if Booger isn't speaking"). **2026-08-15 bugfix: the `state != "idle"` guard around those four calls was REMOVED -- they now run unconditionally here too.** The old guard meant a hover card already on screen the moment Booger went idle/talking simply stopped being `.Step()`'d, which FROZE it in place (fully visible, stale) instead of letting its own dwell/fade logic ease it away -- it could end up sitting on top of her speech bubble. The same four calls were also added to the new Dealer-intro gate above, for the same reason. Both now rely on a new suppression check (`TutorialCharacterSpeaking()`, `PlotHoverScripts.gml`) consulted by `PlotHoverSuppressed()`/`BuildingHoverSuppressed()` to actually fade the cards out while a tutorial character is up, rather than skipping the Step() call that would let them do so. See `TutorialGuideScripts.md`/`PlotHoverScripts.md`.

**Fate Engine lock (2026-08-13, whole-tutorial scope, independent of `restrictionActive`).** The XP-bar-click block below (which opens the Fate Engine overlay) now checks `!global.tutorialGuide.fateEngineLocked` before calling `.Open()`, still `exit`-ing either way -- consumes the click, silently no-ops while locked. `fateEngineLocked` is set once at the start of the guided tutorial and stays true for its ENTIRE duration (unlike `restrictionActive`, which clears between phases) -- the request's own framing was that only "gameplay other than the fate engine interface" opens up once the tutorial's final phase ends, so this gate deliberately isn't cleared alongside `restrictionActive`. See `TutorialGuideScripts.md`'s "Fate Engine lock" section.

## Draw_64

Draw order is deliberate top-to-bottom (later calls render on top):

0. `global.tutorialGuide.Draw_Behind()` -- 2026-08-13, ABSOLUTELY first (before even the Fate Engine overlay dim) -- Booger is "the lowest item in the UI." Draws ONLY her portrait (2026-08-14). No-ops while hidden. See `TutorialGuideScripts.md`.
1. `fateEngineOverlay.Draw()` -- so its 0.75-alpha dim rect sits BEHIND the persistent UI bar sprites drawn right after, keeping the bar visible on top while the overlay is open. No-ops while closed.
2. Persistent UI bar sprites (`sRulerBar`, `sMainUIBarBottom`, `sUISpellsCloth`).
3. `rulerPortraitController.Draw(27, 1080, 2)` -- bottom-left anchored (matches the portrait sprite's own origin) at scale 2x (`HOVER_CARD_SCALE` convention). `global.tutorialGuide.Draw_Front()` (2026-08-13) draws right after this -- Booger's hands, always above the bar (2026-08-14, was a below/above swap -- see `TutorialGuideScripts.md`). Her speech bubble no longer draws here, see step 4a below.
4. `DrawTrainingQueueBars()` -- room-space positions converted to GUI space (`WorldToGui`) so these render from this Draw GUI event and stay above every room-space Draw call regardless of instance depth.
4a. `global.tutorialGuide.Draw_Bubble()` (2026-08-14, new call site) -- right after `DrawTrainingQueueBars()`, specifically so her speech bubble renders ON TOP of the training-queue progress bars instead of underneath ("draw Booger's speech bubble over top the unit building production bar"). No-ops unless `state == "idle"`. See `TutorialGuideScripts.md`.
5. `orderMenu.Draw()`, `blueprintController.Draw()`, `DrawResourceBar`, `DrawCastleHealthWidget`, `DrawArmyLimitWidget`, `xpBarWidget.Draw()`.
6. Hover/tooltip layer, deliberately last-ish so each renders on top of the panels above it: `plotHoverController.Draw()` -> `buildingHoverController.Draw()` -> `castleBonusHoverController.Draw()` -> `blueprintController.DrawHoverCard()` -> `unitSelectHoverController.Draw()` -> `selectionSummaryMenu.Draw()` -> `castleGarrisonMenu.Draw()` -> `armyLimitMenu.Draw()`.
7. `pauseMenu.Draw()` -- absolutely LAST, on top of the persistent UI bar and every other HUD element (deliberately the OPPOSITE draw-order choice from the Fate Engine overlay, which draws its dim FIRST so the bar stays visible on top of it -- pausing is meant to cover everything, not just the battlefield). No-ops while closed.
