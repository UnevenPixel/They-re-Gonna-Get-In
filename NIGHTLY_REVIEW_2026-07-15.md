## 3. Potential problems

### Worth a direct look

- **`OrderWiring.gml`, "attack" order (lines ~65–86) — likely missing the same fix "defend" just got.** The "defend" order immediately above it (lines 11–50) was bugfixed on 2026-07-13 specifically because `fsm.ChangeState("defend")` no-ops if the unit is *already* in "defend" — redirecting an already-defending unit to a new target silently updated `defendTarget` without re-running `Defend_Enter` to rebuild behavior around it. The fix was passing `_force = true`. The "attack" order right below it has the same shape: it sets `attackBuildingTarget` then calls `fsm.ChangeState(_state)` (line 74) **without** `_force = true`. If a unit already in `"attack"`/`"attackRanged"` gets re-ordered to a *different* building, this looks like the same latent bug — `attackBuildingTarget` updates but `Attack_Enter`/`AttackRanged_Enter` may never re-run to re-approach the new target. `UnitStateAttackMelee.gml`/`UnitStateAttackRanged.gml`'s Step functions weren't cross-checked against this specific question in the same pass that found it, so this needs direct confirmation of whether Step already re-reads `attackBuildingTarget` every frame (which would make it moot) before deciding whether to apply the same `_force = true` fix. This touches load-bearing attack FSM wiring — flagging per CLAUDE.md rather than fixing it directly.

### Worth confirming as intentional

- **`UnitStateSiege.gml` — inconsistent `attackAggroRadius` guarding.** The ASSAULT and RECOVER phases (lines ~172, ~217) guard with `_unit.attackAggroRadius ?? 96`, but the ADVANCE phase's equivalent check (line ~134) and every direct read in `Guard_Step`/`Defend_Step`/`Attack_Step` use it unguarded. Worth confirming whether there's a real path into "siege" where `attackAggroRadius` isn't initialized yet, or whether this is dead defensive code that can be dropped for consistency.
- **`UnitStateAttackMelee.gml`/`UnitStateAttackRanged.gml`/`UnitStateSiege.gml` — shared `_machine.data.cooldownTimer` carried across building-swing and defender/guard sub-phases.** When a DEFENDER (or ENGAGE_GUARD) sub-phase interrupts APPROACH/RECOVER, `cooldownTimer` isn't reset before being reused for the interrupting fight, and whatever state it's left in persists back into the next building-swing timing when the sub-phase exits. May be intentional ("one weapon, one cooldown"), but none of the three files' comments state that as a deliberate design choice. Load-bearing combat states — flagging for confirmation, not touching.
